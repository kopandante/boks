# Прокси boks — Caddy вместо kamal-proxy — 2026-10-06

Цель: boks маршрутизирует трафик через Caddy. Сначала паритет — всё, что boks делает с
kamal-proxy (маршрут на порт, TLS файлом и автоматический, переключение без потерь, откат),
работает так же; затем поверх — то, ради чего переход: маршрут по пути, заголовки, фильтр по
User-Agent на сервер, wildcard-хост.

Автор, 2026-10-06: «Переходим на Caddy».

## Почему (замеры boks-lab, ARM 2 ядра / 12 ГБ, 2026-10-06)

Сверка habsida/tokyo (`20261006-shchr-gaps.md`, G4–G9) упёрлась в то, чего kamal-proxy v0.10.0
не умеет вовсе: заголовки, перезапись пути, фильтр по User-Agent, auth. Caddy умеет всё это штатно.

Память, равные условия (20 TLS-хостов, один сертификат, один бэкенд, 10 генераторов fortio по 30 с,
половина без keep-alive; у Caddy на каждом хосте ещё правило по User-Agent):

| | Caddy 2.11.7 | kamal-proxy 0.10.0 |
|---|---|---|
| простой, RSS / cgroup | 46 / 12 MB | 18 / 6 MB |
| пик под нагрузкой, RSS | 74 MB | 36 MB |
| после нагрузки, RSS / cgroup | 65 / 30 MB | 33 / 22 MB |
| ошибки | 0 | 0 |

+30–40 MB к kamal-proxy; Traefik под Dokploy на наших серверах — 46–156 MB по `docker stats`.
Пропускная способность одинаковая, но упёрлась в CPU машины (генераторы на ней же) — не сравнение.

## Главный факт, который определяет конструкцию

Первый замер (fortio, `caddy:2-alpine`) показал ошибки на каждом изменении конфига — ~20 на
изменение под нагрузкой и для `caddy reload`, и для PATCH через admin API, — и отсюда был сделан
вывод «любое изменение конфига рвёт соединения». **Как общий вывод он неверен.** Внешний разбор
(codex) показал по исходникам Caddy 2.11.7, что reload плавный (SO_REUSEPORT, `grace_period` по
умолчанию не ограничен), и причина ошибок была найдена экспериментом: сбрасываются соединения,
ждущие в очереди accept закрывающегося SO_REUSEPORT-слушателя. Ядро ≥ 5.14 переносит их на соседний
слушатель при `net.ipv4.tcp_migrate_req=1`.

boks-lab, `caddy:2.11.7-alpine`, ядро 6.17, клиент на Go, 10 reload под 40 соединениями:

| режим | reset | EOF |
|---|---|---|
| static_response, без апстрима | 41 | 170 |
| static + `tcp_migrate_req=1` | 0 | 142 |
| reverse_proxy | 93 | 102 |
| reverse_proxy + `tcp_migrate_req=1` | 0 | 87 |
| reverse_proxy + `tcp_migrate_req=1`, клиенты keep-alive | 0 | 0 |

**Вывод:** reset — очередь accept закрывающегося слушателя, `tcp_migrate_req=1` убирает их
полностью; остаточные EOF только у клиентов без keep-alive (~9 на reload при ~1700 новых
соединений/с); с keep-alive — 0. Значит, деплой может переключать трафик reload'ом конфига, как
kamal-proxy переключал своей командой.

Ещё проверено (`caddyfacts.sh`, `caddydrain.sh`): после reload старый сервер Caddy дорабатывает
запросы к прежней копии, и `/reverse_proxy/upstreams` показывает их число, пока они не кончатся;
reload неизменного конфига новые файлы сертификата не перечитывает, `--force` и изменённый конфиг —
перечитывают; конфиг с отсутствующим файлом Caddy отвергает, старый продолжает работать; чужой
`X-Forwarded-For` посетителя Caddy не пропускает (решение #48 сохраняется без настройки).

Скрипты всех замеров — `docs/measurements-2026-10-06-caddy/` (`caddyreuse.sh` гоняет Go-клиент
`/tmp/hammer`, который скрипт не собирает).

## Конструкция

- **Маршрут порта**: хост → `reverse_proxy` со статическим `dial` на имя контейнера копии и порт
  (как target kamal-proxy). Прокси входит в сеть `boks-<app>` приложений, которые маршрутизирует,
  как сейчас. Смена номера порта между релизами решается сама: dial — конкретный контейнер и его
  порт.
- **Прокси** запускается с `--sysctl net.ipv4.tcp_migrate_req=1`; boot проверяет значение в
  контейнере и отказывает, если оно не 1 (ядро старше 5.14 не даст стартовать — тоже понятный отказ).
- **Деплой, overlap**: новая копия стартует → boks опрашивает здоровье каждого порта из контейнера
  прокси (`wget`, `health_path` или `/up`, `health_port`, 5 с на попытку, в пределах
  `deploy_timeout`) → фрагмент приложения и **один reload всех портов разом** под замком допуска →
  drain: пока у адресов старой копии есть запросы в полёте (`/reverse_proxy/upstreams`), но не дольше
  `drain_timeout` (30s, как у kamal-proxy) → `retire`.
- **Неудача**: нездоровая копия в конфиг не попадала — её удаляют. Неудачный reload может пройти без
  ответа, поэтому маршруты возвращаются принудительным reload на прежний фрагмент (старые копии в
  overlap живы), и только потом новая копия удаляется; не удалось вернуть — новая копия остаётся,
  операция в журнале открыта.
- **Stop-first**: старые копии останавливаются, новая стартует, опрос здоровья, reload. При неудаче
  маршруты возвращаются на остановленные копии до того, как они стартуют снова.
- **Состояние маршрутов**: фрагмент на приложение `.boks/_proxy/routes/<app>.json`, применённый
  конфиг `.boks/_proxy/caddy.json` (его загружает стартующий Caddy). Каталог `_proxy`, а не `proxy`:
  там жили бы релизы приложения с именем proxy, а каталог монтируется в прокси. Reload — только когда
  собранный конфиг отличается от применённого. Порядок: `caddy.next.json` → reload → фрагмент →
  `caddy.json`; отвергнутый Caddy конфиг в файлах не остаётся. Применённая ревизия — сам
  `caddy.json`: обрыв между reload и записью виден следующему запуску как расхождение собранного и
  применённого конфига (и как открытая операция в журнале).
- **TLS**: хосты под `cert:` — `load_files` и `skip_certificates`; остальные — автоматический ACME
  Caddy, хранилище в томе `boks-proxy-data`. Продление = установка файлов + `caddy reload --force`
  под замком допуска (пути не меняются, а reload неизменного конфига файлы не перечитывает). Пути с
  поколением (решение #19 о каталогах-поколениях) не сделаны — см. вопросы.
- **X-Forwarded-***: `trusted_proxies` не задан, тест конфига это проверяет. Пользовательские
  `header_up` (C3) не должны задавать For/Proto/Host.
- **Переход с kamal-proxy**: `boks proxy migrate` — маршруты из текущих релизов приложений, dial —
  контейнер, куда kamal-proxy шлёт хост сейчас; pull до остановки; kamal-proxy останавливается и
  отходит под именем `boks-proxy.kamal`, Caddy стартует; не поднялся — kamal-proxy возвращается.
  Хост, который kamal-proxy маршрутизирует и ни один релиз не описывает, — отказ без изменений.

## Рассмотрено и отвергнуто: переключение DNS-алиасом

Первая конструкция: маршрут звонит на имя Docker DNS (`dynamic_upstreams` source `a`, `refresh 1s`,
`try_duration 5s`) в отдельной сети маршрутов `boks-<app>.routes`, boks двигает алиас между копиями,
конфиг не меняется при деплое. На 30 переключениях она дала 0 ошибок (`caddydns.sh`), но после
пересмотра вывода о reload отвергнута по доводам codex:

- **нет фазы drain**: копия, у которой забрали алиас, уходит с запросами в полёте, а Caddy об этом
  не знает; у reload drain есть — старый сервер дорабатывает свои запросы;
- **кэш `dynamic_upstreams` source `a` раздельный по портам**: каждый маршрут перечитывает имя по
  своему таймеру, так что порты одной копии переключаются не атомарно;
- **lookup под общей блокировкой** (`aAaaaMu`): медленный ответ DNS задерживает все маршруты;
- **нет stale fallback**: неудачный lookup оставляет маршрут без апстримов.

## Чего Caddy не решает (честно)

- **Обновление самого прокси (G3)**: смена образа Caddy — перезапуск контейнера на 80/443, как и
  у kamal-proxy. Не хуже, но и не лучше.
- **Клиенты без keep-alive** видят остаточные EOF на каждом reload (~9 на reload при ~1700 новых
  соединений/с); с keep-alive — 0. Reload теперь на каждом деплое.

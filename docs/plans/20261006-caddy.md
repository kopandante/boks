# Прокси boks — Caddy вместо kamal-proxy — 2026-10-06

Цель: boks маршрутизирует трафик через Caddy. Сначала паритет — всё, что boks делает с
kamal-proxy (маршрут на порт, TLS файлом и автоматический, переключение без потерь, откат),
работает так же; затем поверх — то, ради чего переход: маршрут по пути, заголовки, фильтр по
User-Agent на сервер, wildcard-хост.

Автор, 2026-10-06: «Переходим на Caddy».

## Почему (замеры boks-lab, ARM 2 ядра / 12 ГБ, 2026-10-06)

Сверка habsida/tokyo (`20261006-shchr-gaps.md`, G4–G9) упёрлась в то, чего kamal-proxy v0.10.0
не умеет вовсе: заголовки, перезапись пути, фильтр по User-Agent, auth. Caddy умеет всё это штатно.

Память, равные условия (20 TLS-хостов, один сертификат, один бэкенд, 10 генераторов fortio по 30 с,
половина без keep-alive; у Caddy на каждом хосте ещё правило по User-Agent):

| | Caddy 2.11.7 | kamal-proxy 0.10.0 |
|---|---|---|
| простой, RSS / cgroup | 46 / 12 MB | 18 / 6 MB |
| пик под нагрузкой, RSS | 74 MB | 36 MB |
| после нагрузки, RSS / cgroup | 65 / 30 MB | 33 / 22 MB |
| ошибки | 0 | 0 |

+30–40 MB к kamal-proxy; Traefik под Dokploy на наших серверах — 46–156 MB по `docker stats`.
Пропускная способность одинаковая, но упёрлась в CPU машины (генераторы на ней же) — не сравнение.

## Главный факт, который определяет конструкцию

Первый замер (fortio, `caddy:2-alpine`) показал ошибки на каждом изменении конфига — ~20 на
изменение под нагрузкой и для `caddy reload`, и для PATCH через admin API, — и отсюда был сделан
вывод «любое изменение конфига рвёт соединения». **Как общий вывод он неверен.** Внешний разбор
(codex) показал по исходникам Caddy 2.11.7, что reload плавный (SO_REUSEPORT, `grace_period` по
умолчанию не ограничен), и причина ошибок была найдена экспериментом: сбрасываются соединения,
ждущие в очереди accept закрывающегося SO_REUSEPORT-слушателя. Ядро ≥ 5.14 переносит их на соседний
слушатель при `net.ipv4.tcp_migrate_req=1`.

boks-lab, `caddy:2.11.7-alpine`, ядро 6.17, клиент на Go, 10 reload под 40 соединениями:

| режим | reset | EOF |
|---|---|---|
| static_response, без апстрима | 41 | 170 |
| static + `tcp_migrate_req=1` | 0 | 142 |
| reverse_proxy | 93 | 102 |
| reverse_proxy + `tcp_migrate_req=1` | 0 | 87 |
| reverse_proxy + `tcp_migrate_req=1`, клиенты keep-alive | 0 | 0 |

**Вывод:** reset — очередь accept закрывающегося слушателя, `tcp_migrate_req=1` убирает их
полностью; остаточные EOF только у клиентов без keep-alive (~9 на reload при ~1700 новых
соединений/с); с keep-alive — 0. Значит, деплой может переключать трафик reload'ом конфига, как
kamal-proxy переключал своей командой.

Ещё проверено (`caddyfacts.sh`, `caddydrain.sh`): после reload старый сервер Caddy дорабатывает
запросы к прежней копии, и `/reverse_proxy/upstreams` показывает их число, пока они не кончатся;
reload неизменного конфига новые файлы сертификата не перечитывает, `--force` и изменённый конфиг —
перечитывают; конфиг с отсутствующим файлом Caddy отвергает, старый продолжает работать; чужой
`X-Forwarded-For` посетителя Caddy не пропускает (решение #48 сохраняется без настройки).

Скрипты всех замеров — `docs/measurements-2026-10-06-caddy/` (`caddyreuse.sh` гоняет Go-клиент
`/tmp/hammer`, который скрипт не собирает).

## Конструкция

- **Маршрут порта**: хост → `reverse_proxy` со статическим `dial` на имя контейнера копии и порт; маршрут
  с wildcard-хостом идёт после точных (Caddy берёт первый совпавший, kamal-proxy предпочитал точный)
  (как target kamal-proxy). Прокси входит в сеть `boks-<app>` приложений, которые маршрутизирует,
  как сейчас. Смена номера порта между релизами решается сама: dial — конкретный контейнер и его
  порт. `response_header_timeout` 30s — response timeout kamal-proxy: копия, принявшая запрос и не
  ответившая заголовками, даёт 504, а не держит его вечно (по умолчанию у Caddy срока нет).
  `health_path` без ведущего `/` значит то же, что у kamal-proxy (`up` → `/up`). Заголовок
  `Forwarded` удаляется (kamal-proxy его срезал, Caddy пропускает), журнал запросов включён (kamal-proxy
  писал каждый запрос, Caddy по умолчанию — ни одного).
- **Прокси** запускается с `--sysctl net.ipv4.tcp_migrate_req=1`; boot проверяет значение в
  контейнере и отказывает, если оно не 1 (ядро старше 5.14 не даст стартовать — тоже понятный отказ).
- **Деплой, overlap**: новая копия стартует → boks опрашивает здоровье каждого порта из контейнера
  прокси (`wget`, `health_path` или `/up`, `health_port`, 5 с на попытку; порты по очереди, каждый в
  пределах своего `deploy_timeout`, как kamal-proxy ждал каждый маршрут; проходит итоговый статус 2xx после редиректов, как у kamal-proxy, — по строке
  статуса, не по коду выхода busybox wget, который 207 отвергает, а 302 без Location пропускает) → фрагмент приложения и **один reload всех портов разом** под замком допуска →
  drain: пока у адресов старой копии есть запросы в полёте (`/reverse_proxy/upstreams`), но не дольше
  `drain_timeout` (30s, как у kamal-proxy) → `retire`.
- **Неудача**: нездоровая копия в конфиг не попадала — её удаляют. Неудачный reload может пройти без
  ответа, поэтому маршруты возвращаются принудительным reload на прежний фрагмент (старые копии в
  overlap живы), и только потом новая копия удаляется; не удалось вернуть — новая копия остаётся,
  операция в журнале открыта.
- **Stop-first**: старые копии останавливаются, новая стартует, опрос здоровья, reload. При неудаче
  маршруты возвращаются на остановленные копии до того, как они стартуют снова. До остановки boks
  спрашивает Caddy (`caddy validate`), примет ли он конфиг с новыми маршрутами: reload грузит файлы
  сертификатов всех приложений, и файл, испорченный оборванным `boks cert`, после остановки оставил
  бы приложение без копии.
- **Состояние маршрутов**: фрагмент на приложение `.boks/_proxy/routes/<app>.json`, применённый
  конфиг `.boks/_proxy/caddy.json` (его загружает стартующий Caddy). Каталог `_proxy`, а не `proxy`:
  там жили бы релизы приложения с именем proxy, а каталог монтируется в прокси. Reload — только когда
  собранный конфиг отличается от применённого. Порядок: фрагмент → `caddy.next.json` → reload →
  `caddy.json`. Применённая ревизия — сам `caddy.json`: обрыв в любом месте после записи фрагмента
  виден следующему запуску любого приложения как расхождение собранного и применённого конфига, и он
  перезагружает Caddy с маршрутами оборванного запуска (и операция в журнале открыта). Фрагмент после
  reload этого не давал: обрыв между ними оставлял фрагмент и `caddy.json` согласными на старые
  маршруты, и деплой другого приложения молча возвращал маршруты на прежнюю — в stop-first
  остановленную — копию. Отвергнутый Caddy конфиг снимает вызывающий: любая неудача после записи
  фрагмента возвращает маршруты принудительным reload с прежним фрагментом. Возврат маршрутов пишет
  фрагмент, наоборот, после reload: копии, куда маршруты возвращаются, в stop-first ещё остановлены, а
  копия, с которой они уходят, остаётся до успешного возврата — неудачный возврат оставляет фрагмент
  на ней. Правило одно: фрагмент всегда называет копии, живые при обрыве в этом месте. Любая загрузка конфига —
  деплой, продление сертификата, `boks proxy boot` — собирает его из фрагментов, а не берёт
  `caddy.json` как лежит; boot догоняет отстающий `caddy.json` (reload работающего прокси или
  перезапись перед стартом остановленного). Остаток: Caddy, перезапущенный самим Docker (перезагрузка
  хоста) в окне оборванного запуска, загрузит отстающий `caddy.json` до следующего запуска boks.
- **Потоки (WebSocket)**: у каждого маршрута `stream_close_delay` 24h. По умолчанию Caddy закрывает
  потоки сразу, как только reload выгружает конфиг, через который они шли, — а reload теперь на каждом
  деплое и общий для всех приложений: деплой одного рвал бы WebSocket всех остальных (boks-lab2:
  reload, менявший только чужой хост, закрыл поток сразу; с задержкой — нет). kamal-proxy, меняя по
  одному сервису, чужих потоков не трогал. Потоки заменяемой копии считаются в
  `/reverse_proxy/upstreams` (проверено), так что drain ждёт их до `drain_timeout`, а `retire`
  закрывает — как у kamal-proxy.
- **TLS**: хосты под `cert:` — `load_files` и `skip_certificates`; остальные — автоматический ACME
  Caddy, хранилище в томе `boks-proxy-data`. Продление = установка файлов + `caddy reload --force`
  конфига, собранного из фрагментов (не `caddy.json` как лежит — он может отставать от оборванного
  запуска), под замком допуска (пути не меняются, а reload неизменного конфига файлы не перечитывает). Пути с
  поколением (решение #19 о каталогах-поколениях) не сделаны — см. вопросы.
- **X-Forwarded-***: `trusted_proxies` не задан, тест конфига это проверяет. Пользовательские
  `header_up` (C3) не должны задавать For/Proto/Host.
- **Переход с kamal-proxy**: `boks proxy migrate` — маршруты из текущих релизов приложений, dial —
  контейнер, куда kamal-proxy шлёт хост сейчас; pull до остановки; kamal-proxy останавливается и
  отходит под именем `boks-proxy.kamal`, Caddy стартует; не поднялся — kamal-proxy возвращается.
  Хост, который kamal-proxy маршрутизирует и ни один релиз не описывает, — отказ без изменений. TLS
  маршрута и файл сертификата — как kamal-proxy отдаёт хост сейчас (`list --json` и его файл
  состояния), а не из снимка релиза: откат оставляет сегодняшние `tls` и `cert` и указывает current
  на релиз, записанный с другими. Оборванный переход
  продолжается повторным `boks proxy migrate`: kamal-proxy, остановленный под своим именем или
  оставшийся под `boks-proxy.kamal` без Caddy, возвращается (остановка, если ещё идёт, дожидается) и
  переводится заново; Caddy на месте при kamal-proxy в стороне — Caddy
  поднимается, kamal-proxy удаляется (его маршруты к тому времени устарели, сам он не возвращается).
  Цели kamal-proxy читаются после замков всех приложений; замок деплоя, взятый не этим запуском (первый
  деплой приложения без current), — отказ. Неудачный `docker stop` kamal-proxy (ответ мог потеряться
  после остановки) — kamal-proxy запускается снова.
  Фрагменты после перехода — ровно то, что отдаёт kamal-proxy: оставшиеся от оборванного перехода
  у приложений без маршрутов удаляются. Деплой приложения, снимающего маршруты, на сервере, где ещё
  kamal-proxy, — отказ с просьбой о переходе: его маршруты у kamal-proxy, и удалённые копии оставили
  бы их на 502.

## Рассмотрено и отвергнуто: переключение DNS-алиасом

Первая конструкция: маршрут звонит на имя Docker DNS (`dynamic_upstreams` source `a`, `refresh 1s`,
`try_duration 5s`) в отдельной сети маршрутов `boks-<app>.routes`, boks двигает алиас между копиями,
конфиг не меняется при деплое. На 30 переключениях она дала 0 ошибок (`caddydns.sh`), но после
пересмотра вывода о reload отвергнута по доводам codex:

- **нет фазы drain**: копия, у которой забрали алиас, уходит с запросами в полёте, а Caddy об этом
  не знает; у reload drain есть — старый сервер дорабатывает свои запросы;
- **кэш `dynamic_upstreams` source `a` раздельный по портам**: каждый маршрут перечитывает имя по
  своему таймеру, так что порты одной копии переключаются не атомарно;
- **lookup под общей блокировкой** (`aAaaaMu`): медленный ответ DNS задерживает все маршруты;
- **нет stale fallback**: неудачный lookup оставляет маршрут без апстримов.

## Чего Caddy не решает (честно)

- **Обновление самого прокси (G3)**: смена образа Caddy — перезапуск контейнера на 80/443, как и
  у kamal-proxy. Не хуже, но и не лучше.
- **Клиенты без keep-alive** видят остаточные EOF на каждом reload (~9 на reload при ~1700 новых
  соединений/с); с keep-alive — 0. Reload теперь на каждом деплое.
- **Заголовки запроса с `_` и `.` в имени** (`X_Auth_Token`) Caddy 2.11.7 отбрасывает — защита
  CGI/Rack-бэкендов от подмены через нормализацию; kamal-proxy их пропускал. Принято как намеренное
  изменение (ревью #66); понадобится приложению — пропуск поимённо в порту.
- **`X-Request-ID` и `X-Request-Start`** kamal-proxy ставил, если их не было; Caddy не ставит. Пробел
  паритета, отложен: в boks.yml нет приложения, которое на них опирается.
- **Двойной сбой связи при возврате маршрутов** (ревью #66, HIGH): если в одном stop-first запуске
  ответ SSH теряется дважды, приложение может остаться на 502, а boks печатает ошибку с описанием
  состояния. Принято для C1; отдельная задача — судить о том, что работает в Caddy, по его admin API, а
  не по файлам.
- **ACME-сертификаты kamal-proxy** при `boks proxy migrate` не переносятся (ревью #66): хост с TLS
  без `cert:` Caddy обслуживает, когда получит свой сертификат по HTTP-01 после старта; до этого
  TLS-рукопожатие к хосту не проходит, а при недоступном Let's Encrypt — пока заказ не пройдёт. Том
  `boks-proxy-config` с сертификатами kamal-proxy остаётся; migrate советует удалить его, только когда
  Caddy отдаёт все хосты по HTTPS. Хосты под `cert:` (файл) переходят без паузы — так проверено на boks-lab.
- **Неизвестный хост на :80** kamal-proxy отвечал 404; Caddy в C1 — 308 на HTTPS, если на сервере есть
  хост с TLS, иначе пустой 200 (boks-lab2, ревью #66). Свой сервер на :80 с 404 — в #67.
- **Журнал запросов** включён (ревью #66), поэтому у контейнера прокси ротация логов Docker:
  5 × 10 MB. Прокси, созданный раньше, получает её при пересоздании (G3).

Решения по ревью #66 приняты по умолчанию 2026-10-06, автор может отменить. WebSocket после reload
держится до 24 ч (`stream_close_delay`), ответ приложения ждём не дольше 30 с, как kamal-proxy.

      - файл фрагмента начинается с номера формата (2): boks C1 на нём останавливается с ошибкой, а не
        перезагружает прокси без путей и правил заголовков, которых не знает; формат новее своего — отказ
- [x] **C5. Фильтр по User-Agent на сервер** (G9) — конструкция ниже. Решение автора 2026-10-06 (основание — разбор
      codex, пункт 4): серверные настройки живут в отдельном `server.yml` в инфраструктурном
      репозитории, не в `boks.yml` приложения. Применяются явной командой (рабочее имя
      `boks server apply -f server.yml`), которая кладёт версионированную копию в серверное
      состояние (`.boks/server/`) под серверным замком, с журналом, ожидаемой ревизией (устаревший
      CI не перезаписывает более новую политику) и откатом. Обычный deploy читает уже применённую
      серверную политику и меняет только фрагмент своего приложения; сборщик конфига Caddy
      объединяет серверную политику и фрагменты приложений. С приходом boksd меняется только
      транспорт (API вместо SSH). Для UA-фильтра заранее определить область (весь прикладной HTTP),
      исключения и приоритет, поведение на неизвестном Host и то, что ACME challenge не режется

## Конструкция C5 — серверная политика и фильтр ботов

Образец — `bot-policy.yml` и `telegram-images-allow.yml` на Habsida (ручные файлы Traefik, 2026-08-04
и 2026-08-15): на `*.habsidev.com` 403 любому боту, на остальных хостах 403 краулерам, кроме Google и
Яндекса; загрузчик Telegram пропускается на пути картинок одного хоста над всеми блоками. Конструкция
пересмотрена по разбору codex (2026-10-06, пункты в скобках).

```yaml
# server.yml — в инфраструктурном репозитории, не в boks.yml приложения
servers: [habsida]
revision: 4              # следующая после наивысшей применённой, как serial зоны DNS
bots:
  allow:                 # важнее любого блока (8)
    - host: backends-encar.v1.backend.dev.habsidev.com
      paths: [/pics, /pics_i]          # префикс с границей, как path порта (C2)
      user_agent: "(?i)telegrambot"
  block:
    - name: infra
      domains: [habsidev.com]          # домен и все хосты под ним на любой глубине (3)
      user_agent: "(?i)(bot|crawler|spider|...)"   # RE2, как у Caddy
    - name: crawlers                   # без domains — все хосты, и неизвестные
      user_agent: "(?i)(bingbot|gptbot|ahrefsbot|...)"
```

- **Смысл**: запрос, подходящий под домены и `user_agent` блока, получает 403 без тела, если не подходит
  ни под один `allow`; запрос, пропущенный allow, идёт обычной маршрутизацией. Блоки стоят первыми на
  :80 и :443 — раньше маршрутов приложений, редиректа на HTTPS и 404. `/.well-known/acme-challenge/`
  исключён явно (Caddy и так отвечает на HTTP-01 раньше маршрутов — server.go, HandleHTTPChallenge;
  TLS-ALPN-01 идёт на рукопожатии, фильтр его не видит).
- **Домены — шаблоном по Host, не матчером host** (3, 6): матчер Caddy `*.x` берёт один уровень, а
  каждый хост из матчера на :443 Caddy берёт в выпуск сертификата. allow — внутри `not`, туда обнаружение
  сертификатов не заглядывает, поэтому его хост — обычный матчер.
- **:80 — свой сервер boks** (4, 5): редиректы Caddy выключены (`disable_redirects`), при TLS-хостах :80
  есть всегда — блоки, HTTP-маршруты, 308 для TLS-хостов, 404. Иначе Caddy ставит свой сервер на :80,
  который о фильтре не знает, или вставляет редиректы по собственным правилам. Это и паритет C1: с одними
  `cert:`-хостами Caddy своих редиректов не вставлял, и 404 из C2–C4 их перекрывал.
- **Ревизия** (10, 11): принимается следующая после наивысшей применённой (`floor + 1`); та же ревизия с
  той же политикой, что сервер применяет сейчас, — повтор (доводит файлы); прочее — отказ до изменений:
  устаревший CI или правка от той же ревизии. Сервер без политики берёт любую — так входит новый сервер
  парка. Все серверы файла опрашиваются до первого изменения. Не CAS по содержимому: правка, поднявшая
  ревизию через одну, пройдёт — ревизия растёт на один, это и есть договор.
- **Состояние**: `.boks/_server/` (`server` может быть именем приложения, как и `proxy`):
  `policy.json` (политика, `revision`, `floor`), `history/<revision>.json` (только применённые),
  `journal.jsonl`.
- **Порядок записи** (12–14): политика пишется до reload — иначе запуск, оборванный после того, как Caddy
  принял конфиг, оставил бы на диске старую, и деплой любого приложения собрал бы из неё конфиг без
  фильтра. Записанная заранее, она доводится следующим reload любого запуска. Неудачный reload
  возвращает прежнюю политику и перезагружает её принудительно (ответ мог потеряться после того, как
  Caddy принял новую). История — последней. Всё под замком допуска сервера, в журнале.
- **Откат** (`boks server rollback server.yml <revision>`): политика из `history/`, `floor` не
  опускается — откатанный файл не вернётся, следующая правка — `floor + 1`. **Статус**
  (`boks server status server.yml`): ревизия, `floor`, число правил, незакрытый запуск.

Проверено на boks-lab (`measurements-2026-10-06-caddy/c5live.sh`): конфиг, собранный `Config()` boks
для политики Habsida, в Caddy 2.11.7 — 16 из 16 случаев как ожидалось (allow с границей префикса, домен
с регистром и портом, ACME-путь, 308 и 404 на :80, неизвестный хост), выпуска сертификатов для доменов
фильтра в журнале Caddy нет.

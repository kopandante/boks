# Hairpin: контейнер узла достаёт прокси своего же узла (2026-10-08)

## Инцидент

8 октября хосты приложений на hb-sites, hb-pooldb и hb-poolapi перевели на прямой DNS: имя
указывает на сам узел. Сразу сломалась авторизация во всех Convex («fetch failed»). Convex Auth и SSR
Next.js ходят на свой `*-convex-site` по публичному имени, а теперь это имя резолвится в адрес того же
узла.

Механизм, прочитанный на hb-sites (Docker 26.1.5, iptables-nft): в `nat DOCKER` на каждый мост
стоит `-i br-… -j RETURN`, поэтому соединение из контейнера на публичный адрес узла не транслируется
DNAT. Оно уходит в INPUT хоста к `docker-proxy`, который слушает `0.0.0.0:443`. Цепочка `inet filter
input` хоста (`policy drop`) принимала с `br-*` только `ip daddr 10.88.0.0/24` и отбрасывала такое
соединение. С самого узла запрос идёт через `lo`, поэтому проверка curl'ом с хоста ничего не видела.
Временная починка — правило в `deploy/egress/nftables-hb.conf` репо backends.

## Решение: вариант Б, правило ставит `server apply`

Альтернатива (А) — алиасы прокси на `host:` всех приложений в сетях Docker. Отклонена по трём
причинам:

- **IP не покрыт.** Алиас отвечает только на имя. Запрос по адресу узла идёт тем же путём через INPUT
  и так же отбрасывается.
- **Обновление алиаса = обрыв.** Алиас задаётся только при `docker network connect`. Чтобы добавить
  хост нового приложения, прокси надо отключить и снова подключить к каждой сети, а это обрыв
  соединений прокси с приложениями.
- **Приложения узла резолвят чужие хосты.** Сайт обращается к хосту своего Convex — это другое
  приложение, и его сети прокси может не знать. Поэтому в каждой сети нужны алиасы всех хостов узла,
  и любой новый хост переподключает прокси везде.

Б — правило в input-цепочке хоста. Отдельная таблица nft не помогает: `accept` в одной базовой
цепочке не отменяет `drop` в другой на том же хуке. Поэтому правило вставляется в саму цепочку
хоста, и такая вставка теряется при перезагрузке конфига хоста. Чтобы она держалась, boks кладёт
drop-in в `nftables.service`: правило возвращается после start, restart, reload и загрузки.
Проверено на Debian 13 / Docker 26.1.5 в OrbStack.

## Работы

- [x] `internal/deploy/hairpin.go`: чтение фактов (`nft -j list chains`, nftables.service, файлы boks),
      скрипт, который вставляет правило один раз, drop-in, `EnsureHairpin`
- [x] `server apply` вызывает `EnsureHairpin` на каждом сервере после применения политики
- [x] `CheckHairpin`: после `boks deploy` для каждого TLS-хоста приложения временный контейнер в
      `boks-<app>` (образ работающего прокси) делает запрос `https://<host>/`; без ответа — ошибка, deploy
      завершается с ненулевым кодом
- [x] ревью (review-loop --ship): шаг firewall под замком допуска; `daemon-reload`, если systemd не
      прочитал drop-in; проба — один контейнер, `--add-host <host>:<src из ip route get>` (прокси этого
      сервера, что бы ни говорил DNS), `timeout 20` на запрос, хост-адрес не проверяется
- [x] тесты по образцу `server_test.go` / `deploy_test.go`
- [x] `docs/architecture.md`: раздел «Сеть» и рядом с R4
- [x] живая проверка на OrbStack Debian 13 (Docker 26.1.5, nftables 1.1.3), конфиг nft как у hb без
      временного правила, хост `app.192-168-139-145.nip.io` с `tls: true`:
  - `proxy boot`, deploy → проверка падает: `Connecting to … (192.168.139.145:443) wget: download timed out`;
  - `server apply` → `inserted into inet filter input`, повтор ничего не пишет, deploy проходит;
  - `systemctl reload nftables`, `systemctl restart nftables`, перезагрузка машины → правило на месте,
    deploy проходит;
  - `nft -f /etc/nftables.conf` в обход юнита → правила нет, deploy падает, `server apply` возвращает
    правило;
  - из контейнера `boks-hp` по IP узла: `http://192.168.139.145/` → 404 от Caddy
- [ ] после merge, только по слову владельца: `boks server apply` на hb-sites, hb-pooldb и hb-poolapi;
      затем временное правило можно убрать из `deploy/egress/nftables-hb.conf` в backends

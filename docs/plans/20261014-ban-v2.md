## Context

Бан v1 (boks#97/#98) считает все запросы адреса в одном окне. Порог 300/мин банил обычных посетителей:
шаблон сайтов делает до ~95 считаемых запросов на переход (autogroup), клиента autogroup забанило за
5 страниц каталога. Порог временно поднят до 1500/мин (backends#507). При этом:
- ночной обходчик 14.10 (217.81.103.213, headless Chrome, заголовки настоящие) открывал 0–13 страниц в
  минуту и делал до 1 386 API в минуту — лимит по страницам и эвристики «подделки» его не ловят, ловит объём;
- японский шторм на dbauto (72 домашних адреса, по 37 запросов/час на адрес) не ловит никакой лимит
  по адресу; у всех его запросов есть `Sec-Fetch-Mode`, но нет `Sec-Fetch-Site` и `Sec-Fetch-Dest` —
  настоящий браузер шлёт Fetch Metadata только всеми тремя вместе.

Владелец: «нужны разумные лимиты» и «эвристики против штормов вроде японского» — оба «да», без капчи.

Калибровка (Loki hb-sites, 13.10 07:45 → 14.10 07:45 UTC, пик по адресу; скрипт `scratchpad/calib.py`,
вывод `calib.out`; 22 окна из ~250 выпали по таймауту Loki — данные неполные):
- все считаемые, 1 мин: обходчик 1 662, дальше 768 и ниже;
- все считаемые, 10 мин: обходчик 8 452; затем 3 157, 2 983, 2 842; дальше ≤ 1 245 (клиент autogroup — 946 API за 10 мин);
- страницы (GET, не /api/, не prefetch), 1 мин: сверху облачные адреса (GCP/Azure) 220–500 страниц/мин.

## Решение

### 1. Правила вместо одного лимита (proxy/ban, internal/config, internal/proxy)

`ban:` получает список `rules`. Правило: `name` (уникальное, обязательно), `limit`, `window`,
селектор: `class` (`all` по умолчанию | `page` | `api`) И, если задан, `paths` (регэкспы по очищенному
пути) — запрос считается правилом, когда подходит и класс, и пути. Адрес банится на общий `duration`
при превышении любого правила; в журнале — имя правила.
- Классы: `all` — всё, что считается сейчас; `page` — GET, путь не под /api/, без `Next-Router-Prefetch`;
  `api` — путь под /api/.
- Исключения: private-сети, exempt_ranges, bots.allow и exempt_paths действуют на все правила.
  Исключение подресурсов по `Sec-Fetch-Dest` — только для `all` и `page`: правила `api` и с `paths`
  считают запрос к своему эндпоинту, какой бы Dest он ни заявил (заявленный предел v1 для `all` остаётся,
  записан в docs).
- Синтаксис: старые `limit`/`window` верхнего уровня — ровно одно правило `all` с именем `default`, и
  только когда `rules` нет; смешивать `rules` с `limit`/`window` — ошибка конфига; пустой `rules: []` —
  ошибка; не более 16 правил.
- Хранилище: состояние адреса — бан + счётчики по имени правила; у каждого счётчика своё начало окна и
  истечение. Запись адреса удаляется, только когда истекли все её счётчики и бан. Сменилось у правила
  окно или лимит — его счётчик начинается заново при следующем запросе (сравнение по имени + окну);
  удалённое правило — его счётчик удаляется при очистке; бан адреса не зависит от правил и переживает
  любые reload. Provision общее состояние не меняет — только читает (правила передаются в hit).
- Значения для hb-sites (отдельный PR в backends после merge): `all` 1500 / 1m, `all` 2500 / 10m,
  `page` 120 / 1m. Правила с `paths` — механизм есть, значения для hb-sites не ставим, пока нет данных.

### 2. Эвристики (тот же модуль), `heuristics.mode: off | log | ban`, по умолчанию off; hb-sites — log
- **forged** — сильный признак, без разбора UA: запрос несёт `Sec-Fetch-Mode`, но не несёт
  `Sec-Fetch-Site` или `Sec-Fetch-Dest`. Браузеры шлют Fetch Metadata тройкой (Chromium 76+, Firefox 90+,
  Safari 16.4+); старые браузеры не шлют ничего — и не помечаются. Заголовки проходят через hb-edge
  как есть, поэтому признак работает и на прямом, и на проксированном пути; протокол и TLS не используются.
- Слабые признаки — только в журнал для анализа, в кластер и бан не идут: UA Chromium без `sec-ch-ua`
  (WebView/in-app), HTTP/1.x на прямом TLS.
- **cluster** — считаются только запросы с сильным признаком. Отпечаток нормализованный: семейство и
  мажорная версия из UA, первичный тег Accept-Language, набор присутствующих Fetch-Metadata-заголовков.
  Произвольные заголовки в отпечаток не входят — дробление случайными X-* не помогает. Смена UA на
  каждом запросе дробит кластер — этот класс обхода заявлен как предел эвристики.
- Порог: больше `cluster.limit` запросов за `cluster.window` с не менее `cluster.min_addresses` адресов
  → в журнал `cluster flagged`. В режиме ban — 403 запросам с этим отпечатком и сильным признаком на
  `duration`, журнал `fingerprint banned`. Режим проверяется при каждом запросе: ban → log прекращает
  отказы сразу, накопленные баны отпечатков не исполняются. exempt_ranges и bots.allow приоритетнее
  бана отпечатка, как и бана адреса.
- Память: не более 10 000 отпечатков; множество адресов на отпечаток хранится до `min_addresses`
  (потом только флаг); пример UA обрезан до 160 символов; журнал — одна строка на адрес/отпечаток на окно.
  Бюджет худшего случая (200k адресов × 16 счётчиков + 10k отпечатков × min_addresses) измеряется
  тестом, как в v1 (`DefaultMaxTracked`).
- Значения hb-sites: `mode: log`, cluster 300 / 10m, min_addresses 10 (японский шторм — ~1 200 за 10 мин
  с 72 адресов). Через неделю журнала — решение о `mode: ban` отдельным PR.

### 3. Формат и совместимость
- Политика и фрагменты: формат 7 (`FragmentFormat`, internal/proxy/caddy.go). boks формата 6 на сервере
  с политикой формата 7 откажется работать. Новые поля — типизированные, как в v1 (сравнение политик
  через marshal в internal/proxy/policy.go остаётся детерминированным).
- `CheckBan` (internal/proxy/shape.go): в образе прокси (запущенном или остановленном, через
  `docker run --rm <образ> caddy validate`) проверяется маленький конфиг с `rules` и `heuristics`:
  Caddy разбирает модули строго, старый хендлер отвергнет неизвестные поля.
- Откат: политика revision без `rules` и `heuristics` читается новым boks как v1; маркер формата 7
  остаётся — boks ниже версии этого PR на узле работать не будет (флот поднимаем до политики).

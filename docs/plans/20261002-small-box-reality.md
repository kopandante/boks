Цель: boks разворачивает связку glavdoroga (Next + Convex + Redis) на egress-VDS Selectel
136.234.5.122, и решения, которые этот сервер опроверг, пересмотрены с причиной.

Автор, 2026-10-02: «Boks нам как раз и нужен, чтобы обслуживать такие маленькие серверы. И если
реальность противоречит принятым решениям, решения надо пересмотреть.»

## Сервер (факты, измерено 2026-10-02)

- 2 ГБ RAM, 1 vCPU, 25 ГБ, Debian 13; на нём же tinyproxy egress-пула encar (живой прод-путь).
- nftables: `flush ruleset`, input/forward policy drop, таблица fail2ban. Любой reload стирает
  правила Docker → dockerd запущен с `iptables=false`, `bridge=none`.
- Связка сейчас на compose в `network_mode: host` (`cars/clients/glavdoroga/deploy/vds/`),
  проверена полностью (цены = прод до рубля, заявка, админка, honeypot, 200×SSR p95 0.89 с).
  Факт: next 140–200 МБ, convex 126–138, redis 8–16, caddy 16–32.
- Компоненты живут в разном ритме: Convex — закреплённая сборка backend (меняется раз в месяцы),
  Next — образ на каждый коммит, Redis — стоковый образ. Откатываются независимо.

Что сервер **подтвердил** без пересмотра: A1 (без маршрутов → готовность по `HEALTHCHECK` образа;
стоковому Redis — пятистрочный Dockerfile, это и есть путь «только Dockerfile»), E2 (вход в
приватный реестр перед `pull`), B5 (ротация логов), сборка вне сервера.

Новый пробел: **адрес посетителя за kamal-proxy.** Клиенты парка доверяют `X-Forwarded-For`,
потому что прокси его перезаписывает. Поведение kamal-proxy с TLS (перезапись или дописывание,
`X-Real-IP`, `CF-Connecting-IP`) не проверено; ошибка = обход банов и привязки токена к IP.
Проверяется так же, как Caddy на этом сервере: подмена заголовков снаружи + положительный
контроль напрямую в приложение.

## Разбор codex (read-only, 2026-10-02) и замеры на сервере

- **R1 — принят с уточнением.** E1/C5 сами по себе записаны верно (`20260915-decisions.md`), неверна
  только очередь 6. Делать целиком: лимит + резерв + допуск под **серверным** замком (сейчас замок
  на приложение, `internal/deploy/deploy.go:36–45` — два приложения проходят проверку памяти
  одновременно) + фактическая остановка и возврат старого при `stop-first`.
- **R2 — изменён.** «Разный ритм релизов» compose не опровергает: запись не требует совместного
  отката. `uses:` выбран как совместимый с журналом на приложение (`internal/release/release.go`),
  но с контрактом: снимок хранит все сети и алиасы, rollback восстанавливает прежние связи
  (сейчас снимок и откат знают одну `Network`, `release.go:25–37`, `rollback.go:50–60`);
  деплой отказывает до изменений, если зависимость не развёрнута и не здорова; `rm` зависимости
  с потребителями — отказ, `rm` потребителя отсоединяет его от чужих сетей; одинаковые алиасы
  разных владельцев в одной сети — отказ; прокси подключается только к сетям маршрутизируемых
  целей, не транзитивно (`internal/proxy/proxy.go:115–117` сейчас просто `return nil`). Известное
  ограничение: в overlap алиас резолвится в обе версии — потребитель может попасть в неготовую.
  `uses:` — сетевое членство, не ACL: два потребителя одной зависимости видят друг друга.
- **R3 — принят.** Снимается запрет платформы, Postgres — рекомендация. Общий Redis парка —
  отдельное решение (межсерверный доступ, аутентификация, сохранность, поведение при отказе),
  `uses:` его не даёт.
- **R4 — изменён, и сильнее, чем думал codex.** Замер на сервере 2026-10-02: при `iptables=false`
  порт прокси публикует userland `docker-proxy`, и приложение видит **адрес шлюза Docker вместо
  клиента** (Habsida 87.228.113.239 пришла как `X-Forwarded-For: 172.17.0.1`). Все посетители — один
  адрес: один бан закрывает сайт всем. Плюс `ip_forward=0`. Значит, «forward + masquerade в своей
  таблице» недостаточно: нужна публикация с сохранением адреса источника (DNAT), иначе сеть boks на
  таком сервере непригодна. Одна своя таблица также не отменяет чужой `forward policy drop`
  (accept в своей цепочке не перекрывает drop в чужой базовой).
- **Адрес посетителя — проверено на образе v0.10.0** (локально и на сервере, `--tls` + свой
  сертификат): `X-Forwarded-For` **перезаписывается** адресом соединения, `Forwarded` срезается,
  `X-Real-IP` и `CF-Connecting-IP` **проходят как есть** (codex по исходнику: `target.go:322–337`
  чистит только XFF). Клиенты парка берут XFF первым — безопасно; любое прямое чтение `X-Real-IP`
  за kamal-proxy подделываемо.
- **Порядок — изменён:** до #18 расширить снимок релиза (версия формата, сети/алиасы, `uses`,
  память, режим замены — всё, что требует `20260915-decisions.md:18–19`, а в `release.go` нет);
  R4/E3 — до первого запуска сети boks на целевом сервере; compose снимать только после проверки
  независимого отката, удаления зависимостей и reload/reboot firewall.

## Решения автора 2026-10-02

- **R4 → firewall ведёт Docker.** Docker снова сам управляет правилами (DNAT сохраняет адрес
  клиента); `boks server install` делает конфиг хоста совместимым: вместо `flush ruleset` —
  удаление только своей таблицы хоста, в его forward пропускаются мосты boks, `ip_forward`
  постоянный; проверка reload и перезагрузки с живыми tinyproxy и fail2ban.
- **Стопка #33–#38 вливается в main** через `/review-loop` по порядку.

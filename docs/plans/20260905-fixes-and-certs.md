# Правки из сертификации + жизненный цикл сертификатов — план

Две независимые ветки. A — мелкие находки советников, B — то, без чего boks упирается в потолок
лаборатории: wildcard-сертификаты выпускаются и продлеваются руками, а kamal-proxy не перечитывает
файлы с диска (проверено на стенде: нужен повторный `deploy`, 0.05 с, без простоя).

## A. Правки находок (ветка `fix/cert-review-findings`)

- [ ] `deploy`: `revert` берёт порт из ТЕКУЩЕЙ конфигурации — при смене порта между деплоями
      старый контейнер там не слушает, health-check прокси не проходит, маршрут остаётся на новом
      сломанном контейнере. Фикс: писать раскладку портов в лейбл контейнера
      (`boks.ports=api:3210,actions:3211`), `revert` читает лейбл СТАРОГО контейнера; лейбла нет
      (контейнер от прежней версии boks) → прежний путь с предупреждением
- [ ] `config`: отвергать дубли `ports[].name` и дубли `ports[].host` внутри приложения
- [ ] `deploy.prune`: удалять и untagged-образы этого репозитория (`<none>`), иначе диск растёт
      при workflow «тег по SHA»; используемые образы docker удалить не даст
- [x] ~~убрать том `boks-certs`~~ — СНЯТО: судья судил по PR #3 изолированно, а том — приёмник
      ручных сертификатов, он нужен для B

## B. Сертификаты (ветка `feat/cert-lifecycle`)

Обычные домены закрыты autocert kamal-proxy (HTTP-01, ноль конфигурации) — не трогаем. Речь про
wildcard/DNS-01, который нужен и для `*.домен`, и для будущих preview-окружений.

Выпуск остаётся за `lego` (внешний бинарник, как `ssh` и `docker`): свой ACME-клиент в boks — это
переписывание чужой зрелой работы, а библиотека `lego` тянет SDK всех DNS-провайдеров. Токены DNS
часто ограничены по IP (у Cloudflare для `kopanda.ru` — именно так), поэтому выпуск идёт с
ноутбука или из CI, а не с сервера. boks берёт на себя то, что реально болит: доставку файлов и
перезагрузку прокси.

- [ ] `config`: блок `cert` (`domains`, `dns` — имя провайдера lego, `email`, `path` — каталог
      состояния lego); без блока поведение прежнее (autocert)
- [ ] `internal/cert`: запуск `lego run`/`lego renew`, чтение выпущенных файлов, разбор срока
      через `crypto/x509` (без внешних вызовов)
- [ ] доставка: `.crt`/`.key` в том `boks-certs` на каждом сервере, владелец uid 1001
      (пользователь kamal-proxy в образе), режим 640 — иначе прокси не прочитает
- [ ] перезагрузка: повторный `kamal-proxy deploy` тех сервисов приложения, что пользуются
      сертификатом (прокси держит сертификат в памяти; подмена файлов сама по себе не действует)
- [ ] `deploy`: когда блок `cert` задан — передавать `--tls-certificate-path/--tls-private-key-path`
- [ ] CLI: `boks cert issue`, `boks cert renew`, `boks cert status` (subject, notAfter, дней
      осталось — читая PEM с сервера)
- [ ] `examples/renew.yml` — workflow GitHub Actions по расписанию: `boks cert renew` + алерт при
      неудаче (урок Traefik: молчаливый отказ продления жил полгода)

## Проверка

```
go vet ./... && go test ./... && test -z "$(gofmt -l .)"
go build -o boks ./cmd/boks
```

На `boks-lab` (стенд работает, wildcard `*.lab.kopanda.ru` уже выпускался вручную):

```
./boks -f examples/convex-lab/boks.yml cert status      # текущий сертификат и срок
./boks -f examples/convex-lab/boks.yml cert issue       # staging-выпуск, доставка, перезагрузка
openssl s_client -servername actions.lab.kopanda.ru -connect 152.70.59.137:443 </dev/null \
  | openssl x509 -noout -subject -issuer                 # отдан именно новый
./boks -f examples/convex-lab/boks.yml deploy latest    # под curl-циклом: 0 ошибок
```

Смена порта между деплоями с провалом второго порта → маршрут откатывается на СТАРЫЙ порт
(проверка фикса A1 на стенде, не только в тестах).

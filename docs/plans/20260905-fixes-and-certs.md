## B. Сертификаты (ветка `feat/cert-lifecycle`)

Обычные домены закрыты autocert kamal-proxy (HTTP-01, ноль конфигурации) — не трогаем. Речь про
wildcard/DNS-01, который нужен и для `*.домен`, и для будущих preview-окружений.

Выпуск остаётся за `lego` (внешний бинарник, как `ssh` и `docker`): свой ACME-клиент в boks — это
переписывание чужой зрелой работы, а библиотека `lego` тянет SDK всех DNS-провайдеров. Токены DNS
часто ограничены по IP (у Cloudflare для `kopanda.ru` — именно так), поэтому выпуск идёт с
ноутбука или из CI, а не с сервера. boks берёт на себя то, что реально болит: доставку файлов и
перезагрузку прокси.

- [x] `config`: блок `cert` (`domains`, `dns` — имя провайдера lego, `email`, `path` — каталог
      состояния lego); без блока поведение прежнее (autocert)
- [x] `internal/cert`: запуск `lego run`/`lego renew`, чтение выпущенных файлов, разбор срока
      через `crypto/x509` (без внешних вызовов)
- [x] доставка: `.crt`/`.key` в том `boks-certs` на каждом сервере, владелец uid 1001
      (пользователь kamal-proxy в образе), режим 640 — иначе прокси не прочитает
- [x] перезагрузка — **сделано иначе, чем задумано.** План говорил «повторный `kamal-proxy deploy`
      сервисов этого приложения»; вышло `docker restart boks-proxy`. Причина выяснилась на стенде:
      прокси держит сертификаты в памяти ПО СЕРВИСАМ, поэтому повторный deploy освежает только
      маршруты своего приложения, а второе приложение под тем же wildcard продолжает отдавать
      старый. Рестарт заставляет перечитать файлы для всех сервисов и стоит 0.19 с простоя,
      маршруты и TLS переживают. Отсюда же две метки загрузки разного охвата (`.restarted` на весь
      сервер, `.<app>.loaded` на одно приложение) — и правило, что решение о рестарте смотрит
      только на первую
- [x] `deploy`: когда блок `cert` задан — передавать `--tls-certificate-path/--tls-private-key-path`
- [x] CLI: `boks cert issue`, `boks cert renew`, `boks cert status` (subject, notAfter, дней
      осталось — читая PEM с сервера)
- [x] `examples/renew.yml` — workflow GitHub Actions по расписанию. **Сначала отменён, потом
      сделан заново в PR #9.** Первый вариант хранил `.lego` (ключ ACME-аккаунта и приватный ключ
      сертификата) в кэше Actions, а он не хранилище секретов: кэш основной ветки восстанавливается
      прогонами из любой ветки, включая PR. Кэш при этом был не украшением — без состояния lego
      каждый прогон выпускал новый сертификат. Тупик разошёлся, когда померили, что именно lego 5
      читает для решения «пора или нет»: `.crt` плюс `.json`, а приватный ключ в решении не
      участвует. Отсюда `boks cert pull` — забирает с сервера эти два файла и только их. Кэша нет
      вовсе, ключ сертификата не покидает сервер, ключ ACME-аккаунта живёт в секретах репозитория

## Проверка

```
go vet ./... && go test ./... && test -z "$(gofmt -l .)"
go build -o boks ./cmd/boks
```

На `boks-lab` (стенд работает, wildcard `*.lab.kopanda.ru` уже выпускался вручную):

```
./boks -f examples/convex-lab/boks.yml cert status      # текущий сертификат и срок
./boks -f examples/convex-lab/boks.yml cert issue       # staging-выпуск, доставка, перезагрузка
openssl s_client -servername actions.lab.kopanda.ru -connect 152.70.59.137:443 </dev/null \
  | openssl x509 -noout -subject -issuer                 # отдан именно новый
./boks -f examples/convex-lab/boks.yml deploy latest    # под curl-циклом: 0 ошибок
```

Смена порта между деплоями с провалом второго порта → маршрут откатывается на СТАРЫЙ порт
(проверка фикса A1 на стенде, не только в тестах).

# Установка на пустой сервер и открытые вопросы после Caddy — 2026-10-06

Автор, 2026-10-06: «А как вообще мы собираемся устанавливать наш boks на пустой сервер?» — и после
ответа: «Да и по всем остальным вопросам разберись сам с codex».

Сегодня команды установки нет: сервер готовят руками (Docker, SSH-пользователь с доступом к docker,
80/443, ядро ≥ 5.14, cron и flock для расписаний), дальше первый `deploy` или `proxy boot` создаёт
всё сам. Чистая Ubuntu noble готова после
`apt-get install -y docker.io cron util-linux && systemctl enable --now docker cron` (boks-lab2).

Решения ниже — по разбору codex (read-only, 2026-10-06) поверх D2, E3, B5 (`20260915-decisions.md`),
R4 (`20261002-small-box-reality.md`) и G3 (`20261006-shchr-gaps.md`).

## Решения

| # | Вопрос | Решение |
|---|---|---|
| A | Установка на пустой сервер | `boks server install <server.yml>` — для пустого или уже совместимого сервера; чужую инфраструктуру не мигрирует, а отказывает до изменений с точным планом исправления |
| G3 | Смена `proxy_image` у работающего прокси молча игнорируется | Отдельная `boks proxy upgrade` (короткий простой 80/443 — явный контракт); `proxy boot` сообщает о расхождении образов, а не молчит |
| B1 | Хост в Unicode и в punycode у разных приложений (#69) | `golang.org/x/net/idna`, как у Caddy: `idna.ToASCII`, затем нижний регистр — для дубликатов, TLS, сортировки, сертификатов, и для уже записанных фрагментов |
| B2 | Рецепт Redis через `sh -c` запускает redis от root | `exec docker-entrypoint.sh redis-server …`: entrypoint образа сам понижает права (gosu) при первом аргументе `redis-server` |
| B3 | Анонимные тома снятых копий остаются навсегда | `docker rm -v` при окончательном удалении (retire, удаление неудачной новой копии); остановленные в stop-first копии до успеха не удаляются. Именованные тома `-v` не трогает |
| B4 | Расписания у приложения на нескольких серверах | Отказ остаётся (дублирование заданий); сообщение уточняется. Явный `server:` — когда появится потребитель |
| B5 | Вывод одного запуска задания не ограничен | Бюджет на запуск (1 MiB), вывод дочитывается до конца, код выхода — задания; замок до ротации журнала |
| B5' | Ротация логов приложений держится только на настройке демона | Явные `--log-opt` у контейнеров приложений (3 × 10 MB по B5 из `20260915-decisions.md`; прокси — 5 × 10 MB по плану Caddy) |
| B6 | Откат на релиз без `command`/`stop_signal` при заданных сегодня | Предупреждение, как для `memory`; значения не печатаются (в команде бывают секреты), семантика отката не меняется |
| B7 | Каждый вызов — новое SSH-соединение (3,5–4 с до дальнего сервера) | Одно соединение на сервер за запуск: `ControlMaster=auto`, сокеты в каталоге этого запуска под `/tmp`, `Close` закрывает свои; `BOKS_SSH_MUX=0` выключает |
| B8 | `X-Request-ID` / `X-Request-Start` | Позже, до появления потребителя. Способ: нетерминальный маршрут с матчером отсутствующего заголовка и `headers.request.set` перед `reverse_proxy` |
| B9 | Двойной сбой связи при возврате маршрутов | Узко: когда ответ на reload потерян, прочитать `GET /config/` через `docker exec` и сравнить с ожидаемым конфигом этой операции; совпало — подтвердить, иначе как сейчас |

## Работы

- [x] **B7. Общие SSH-соединения** (PR feat/ssh-mux): `remote.Mux`, сокеты в `/tmp/boks-*`
      этого запуска; вызов, отрезанный своим сроком, возвращается не позже чем через 2 с, даже если
      мастер-соединение ещё держит его вывод; keepalive мастера (5 с × 3) ограничивает вызов на
      пропавшую связь, которую `ConnectTimeout` у общего соединения не видит. Замер на boks-lab из `examples/convex-lab` — два
      запуска подряд, `time sh -c 'boks releases >/dev/null && boks ps >/dev/null'`: 27,2 с с
      `BOKS_SSH_MUX=0` и 10,1 с с общими соединениями; после запуска не остаётся ни каталога, ни
      процесса ssh
- [x] **B3, B5', B6, B2, B4** — мелкие правки деплоя и документации (PR feat/deploy-hygiene, #71):
      retire и удаление неудачной новой копии — `docker rm -v`; контейнер приложения — json-file
      3 × 10 MB явными `--log-opt`; откат на релиз без `command`/`stop_signal` при заданных
      сегодня — предупреждение без текста команды; рецепт Redis — через `docker-entrypoint.sh`;
      отказ расписаниям на нескольких серверах говорит, что делать. На boks-lab2: Redis по рецепту —
      PID 1 `redis-server` с uid 999, NOAUTH без пароля; после трёх деплоев подряд остаётся анонимный
      том только текущей копии; `LogConfig` — json-file, max-size 10m, max-file 3
- [x] **B5. Бюджет вывода задания** (PR feat/job-output-cap, #72): `boks-job` пускает вывод запуска
      через FIFO — первые 1 MiB stdout и stderr идут в журнал по ходу запуска (`dd bs=1`, не
      буферизующий `head`), остаток дочитывается до конца и
      считается строкой «output past 1 MiB dropped: about N more bytes»; задание не получает SIGPIPE,
      в `end exit=` — код задания; замок `flock -n` берётся до ротации журнала, и запуск поверх
      идущего пишет пропуск, не переименовывая журнал. `go test ./internal/deploy -run TestRunner`.
      На boks-lab2: приложение `alpine:3.20` с `command: [sleep, infinity]` и расписанием
      `* * * * *` `head -c 2097152 /dev/zero | tr '\0' z; echo done >&2; exit 5` — после
      срабатывания cron в `jobs/big.log` ровно 1048576 байт `z`, «dropped: about 1048581 more
      bytes» (1 MiB + `done\n` из stderr), `end exit=5`, `jobs/big.out` нет; второе расписание
      `echo step1; sleep 20; echo step2; exit 3` — `step1` в `jobs/slow.log` через 7 с после
      старта, во время сна
- [x] **B1. Хосты, как их сравнивает Caddy** (PR feat/idna-hosts, #73): `internal/hostname.Canonical`
      — `idna.ToASCII`, затем нижний регистр, у wildcard `*.` сохраняется; через неё идут дубликаты
      маршрутов в boks.yml и при сборке конфига прокси (значит, и в фрагментах, записанных раньше),
      TLS одного хоста, порядок маршрутов, исключения wildcard и `Cert.Covers`. Заглавные вне ASCII в
      `host` — отказ конфига: Caddy переводит в punycode до смены регистра, браузер — после.
      `go test ./internal/hostname ./internal/config ./internal/proxy`. На boks-lab2: приложение
      `traefik/whoami` с `host: тест.lab2.test` отвечает 200 на `Host: xn--e1aybc.lab2.test` и на
      `XN--E1AYBC.lab2.test`, 404 на чужой хост; второе приложение с `host: XN--E1AYBC.lab2.test` —
      «routed by both idn1 and idn2» до запуска контейнера
- [x] **G3. Обновление прокси** (PR feat/proxy-upgrade, #74): `boks proxy upgrade` под замком допуска
      и в журнале сервера; до остановки — ни одного идущего деплоя, pull, догон отставшего конфига,
      `caddy validate` текущего конфига новым образом; затем старый контейнер отходит в
      `boks-proxy.old`, новый создаётся, подключается к сетям маршрутов, стартует и проверяется
      (admin API, `tcp_migrate_req`), при неудаче возвращается старый — по контейнерам на сервере,
      а не по шагу (ответ docker мог потеряться по дороге); остаток оборванной подмены — отказ с
      точной командой, и раньше, чем «already runs». `proxy boot` работающий прокси не трогает, но называет расхождение
      образов. `go test ./internal/proxy ./internal/deploy -run 'Upgrade|BootNames'`. На boks-lab2 из
      каталога с `boks.yml` приложения `idn1` и нужным `proxy_image`, зонд
      `GET http://<адрес>/` с `Host: xn--e1aybc.lab2.test` каждые 20 мс: `proxy boot` при
      `caddy:2.11.7` — предупреждение, прокси не тронут; `proxy upgrade` на `caddy:2.6-alpine` —
      отказ `unknown field "stream_close_delay"`, прокси не тронут; `2.11.7-alpine` → `2.11.7` и
      обратно, шесть подмен — окно 1,0–1,7 с с общими SSH-соединениями (B7; до 4,5 с, когда
      машина, с которой идёт запуск, перегружена), 2,2–4,0 с с `BOKS_SSH_MUX=0`; у нового прокси
      json-file 5 × 10 MB, в `.boks/_server/journal.jsonl` — `proxy upgrade` с `ok`, отказ
      проверкой записи не оставляет, `boks-proxy.old` не остаётся; прокси, отставленный руками
      (`docker stop boks-proxy && docker rename boks-proxy boks-proxy.old`), — отказ с командой возврата
- [x] **B9. Подтверждение reload через admin API** (PR feat/reload-confirm, #75): когда вызов
      `caddy reload` вернул ошибку, boks читает `GET /config/` через `docker exec` (admin API не
      публикуется) и сравнивает разобранный JSON с порядком массивов: работает конфиг этой
      операции — переключение маршрутов, их возврат или политика подтверждены, запуск идёт дальше;
      работает прежний, отличный от нового, — ошибка говорит, что Caddy остался на нём; спросить не
      удалось — сообщение без утверждений. Перезагрузка ради файлов сертификата (`Reload`) так не
      подтверждается и не опровергается: конфиг тот же. `go test ./internal/proxy -run
      'Lost|PutBack|Unconfirmed|OldConfig'`. На boks-lab2: ответ `/config/` побайтово отличается от
      `.boks/_proxy/caddy.json`, а `jq -S .` у обоих совпадает; обёртка `/usr/local/bin/docker`,
      которая на `caddy reload` отвечает кодом 255 — после выполнения reload (`take`) или не
      выполняя его (`refuse`): `boks deploy v1.10.3` приложения `web` (`traefik/whoami`) при `take` —
      «the reload's answer was lost, but Caddy runs the routes of web», старая копия снята, маршрут на
      новой; `deploy v1.10.2` при `refuse` — возврат маршрутов тоже «потерян» и подтверждён, ошибка
      «Caddy still runs the config it had», новая копия удалена, `Host: web.lab2.test` отвечает 200
      со старой копии
- [ ] **A** — `boks server install`

## Конструкция A (`boks server install`)

- Читает `servers:` из `server.yml`; политику не применяет (это `server apply`), поэтому файлу с
  одними `servers:` ревизия не нужна.
- Сначала предпроверка всех серверов, потом изменения по одному; критичное перепроверяется под
  замком допуска. Отказ: ОС не Debian/Ubuntu с systemd, нет root и `sudo -n`, ядро без
  `tcp_migrate_req`, 80/443 занят не прокси boks (назвать процесс или контейнер), Swarm или rootless
  Docker, `daemon.json` или флаги systemd, противоречащие нужному, firewall хоста, который boks не
  распознаёт (nftables с `flush ruleset`, `iptables=false`) — с адресным планом исправления.
- Пакеты: недостающие из `docker.io`, `cron`, `util-linux`, без общего upgrade; кандидат Docker
  должен поддерживать `--health-start-interval` (API ≥ 1.44), иначе отказ.
- `daemon.json`: структурное слияние, чужие ключи сохраняются, `dockerd --validate`, атомарная
  замена; лог-драйвер json-file 3 × 10 MB; `default-address-pools` — до первой сети boks, без
  пересечений с маршрутами хоста; перезапуск dockerd только при изменении и только без работающих
  контейнеров.
- SSH-пользователь не root — в группу docker; проверка новым соединением, мимо общего.
- Затем `proxy boot`; журнал в `.boks/_server/journal.jsonl`; повтор ничего не меняет.

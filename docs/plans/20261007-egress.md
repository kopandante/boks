# Исходящий прокси в Caddy вместо tinyproxy — 2026-10-07

Автор, 2026-10-07: «Сейчас VDS используются как прокси для сервисов вроде encar-backend» — «Нахера нам
два прокси? Сделай всё через caddy».

Цель: на сервере один прокси — `boks-proxy` (Caddy). Он отвечает и на входящие запросы к сайтам, и
на исходящие запросы сервисов, которым нужен адрес этого сервера. tinyproxy на egress-узлах больше не
нужен. Переключение живого пула — отдельный шаг, только по слову владельца.

## Факты (2026-10-07, только чтение)

- **Пул encar** — четыре VDS Selectel, Debian 13, 1 vCPU / 2 ГБ:
  - 136.234.5.122 и 136.234.5.63 (СПб);
  - 135.106.180.71 и 135.106.210.215 (Москва).
  Список адресов хранится в bws `ENCAR_EGRESS_PROXY_NODES` и в env пяти приложений Habsida.
- **tinyproxy** 1.11.2 на всех узлах, конфиг одинаковый:
  - `Port 3128` на `0.0.0.0`;
  - `Allow` трёх адресов: Habsida, Bravo, Shchr;
  - `BasicAuth` с одним пользователем `encar` (пароль в bws `ENCAR_EGRESS_PROXY_PASSWORD`);
  - `ConnectPort 443` и `80`;
  - `Timeout 60`, `MaxClients 200`, `DisableViaHeader Yes`.
  Тот же список из трёх адресов стоит в nft на порт 3128.
- **Клиенты** ходят по `http://encar:<пароль>@<ip>:3128`, на практике только `CONNECT` на 443:
  - пять приложений на Habsida: encar-backend, encar, dongchedi, che168, dongchedi-login-service;
  - узел выбирают по кругу; после обрыва узел остывает 30 с, после бана — 15 мин.
- **cdn-pin** — systemd-таймер раз в 5 минут, `deploy/egress/cdn_pin.py`:
  - пишет в `/etc/hosts` блок закреплённых адресов CDN che168;
  - прокси должен видеть эти записи при каждом соединении;
  - файл заменяется атомарно (`os.replace`), то есть каждый раз появляется новый inode.
- **Узлы:**
  - узел 1 (136.234.5.122): nftables уже без `flush ruleset` (с 04.10); рядом работает glavdoroga на compose, её Caddy держит 80/443;
  - узлы 2–4: nftables с `flush ruleset`, порты 22, 3128 и больше ничего.
- **Плагин** `github.com/caddyserver/forwardproxy` @ `0aab84d` (2026-03-21) с Caddy v2.11.7
  через xcaddy собирается и работает (проверено на OrbStack 2026-10-07):
  - через прокси проходят `CONNECT` на HTTPS и обычный HTTP, исходящий адрес — адрес хоста;
  - назначение в приватной сети получает 403 (это ACL самого плагина, он ограничивает *назначение*, а не клиента);
  - клиент вне `remote_ip` получает отказ;
  - с `hide_ip`/`hide_via` заголовки о клиенте наружу не уходят;
  - открытый туннель переживает два `caddy reload` подряд: 4 MB скачались целиком, exit 0;
  - разницы в памяти со стоковым образом нет: 11 МБ против 57 МБ в простое (шум сборщика мусора);
  - образ весит 111 MB.

## Решения

| # | Вопрос | Решение |
|---|---|---|
| E1 | Откуда forward proxy | Свой образ `boks-caddy`: `xcaddy build v2.11.7 --with github.com/caddyserver/forwardproxy@0aab84d`, база — `caddy:2.11.7-alpine`. Dockerfile лежит в репозитории (`proxy/Dockerfile`). Сборка для linux/amd64+arm64 — GitHub Actions boks, push в GHCR с `GITHUB_TOKEN`. `DefaultProxyImage` закреплён по digest. Пакет публичный, чтобы серверы тянули образ без входа в реестр (видимость один раз переключает владелец). Работающие прокси меняет `boks proxy upgrade` |
| E2 | Где задаётся | `egress:` в `server.yml`, применяется через `server apply` с ревизией: исходящий прокси — свойство сервера, а не приложения. Поля: `port` (по умолчанию 3128), `allow` (CIDR клиентов, обязателен и не пуст), `user` + `password_env` (имя переменной окружения у оператора; задаются вместе или не задаются вовсе), `ports` (порты назначения, по умолчанию `[443]`), `hosts_file` (см. E5) |
| E3 | Конфиг Caddy | Отдельный HTTP-сервер `egress` на `:<port>` с `automatic_https.disable`. Маршрут: `remote_ip` из `allow` → `forward_proxy` (`hide_ip`, `hide_via`, `allowed_ports`, `auth_credentials`), иначе 403. Политика в журнал запросов не пишет. Аналогов `MaxClients` и `Timeout 60` у плагина нет, это записано как отличие |
| E4 | Пароль | В `policy.json` и `history/` пароля нет (там видно только, что вход задан). Значение лежит в `.boks/_server/egress.secret` с правами 0600 и попадает в `caddy.json`, у которого те же права. Откат политики пароль не трогает. Без переменной окружения `apply` отказывает до изменений |
| E5 | `/etc/hosts` хоста | `hosts_file: /etc/hosts` монтирует файл хоста в прокси только для чтения. Монтирование держит inode, а cdn-pin заменяет файл атомарно, поэтому cdn-pin переходит на запись на месте (усечение и запись одним `write`). Go-резолвер перечитывает файл при смене mtime; в худшем случае окно без закреплений — секунды при смене закреплений |
| E6 | Порт контейнера | Опубликованный порт нельзя добавить работающему контейнеру. Поэтому `server apply`, у которого набор портов `boks-proxy` (80, 443 и порт egress) или монтирование `hosts_file` отличается от нужного, пересоздаёт прокси той же подменой, что `proxy upgrade` (простой около 1–2 с), под тем же замком допуска. Проверка `caddy validate` новым конфигом идёт до остановки старого |
| E7 | Firewall | Порт, который публикует Docker, проходит мимо цепочки input хоста, так что список nft на 3128 перестаёт действовать. Защита эквивалентна tinyproxy: `remote_ip` (как `Allow`) плюс basic auth. На узлах 2–4 `server install` откажет из-за `flush ruleset`: сначала владелец переводит nft на схему узла 1 |
| E8 | Узел 1 | glavdoroga держит 80/443 своим Caddy, `server install` там откажет. Узел 1 переходит последним: после того как glavdoroga переедет под boks (отдельная работа) |

# Исходящий прокси в Caddy вместо tinyproxy — 2026-10-07

Автор, 2026-10-07: «Сейчас VDS используются как прокси для сервисов вроде encar-backend» — «Нахера нам
два прокси? Сделай всё через caddy».

Цель: на сервере один прокси — `boks-proxy` (Caddy). Он отвечает и на входящие запросы к сайтам, и
на исходящие запросы сервисов, которым нужен адрес этого сервера. tinyproxy на egress-узлах больше не
нужен. Переключение живого пула — отдельный шаг, только по слову владельца.

## Факты (2026-10-07, только чтение)

- **Пул encar** — четыре VDS Selectel, Debian 13, 1 vCPU / 2 ГБ:
  - 136.234.5.122 и 136.234.5.63 (СПб);
  - 135.106.180.71 и 135.106.210.215 (Москва).
  Список адресов хранится в bws `ENCAR_EGRESS_PROXY_NODES` и в env пяти приложений Habsida.
- **tinyproxy** 1.11.2 на всех узлах, конфиг одинаковый:
  - `Port 3128` на `0.0.0.0`;
  - `Allow` трёх адресов: Habsida, Bravo, Shchr;
  - `BasicAuth` с одним пользователем `encar` (пароль в bws `ENCAR_EGRESS_PROXY_PASSWORD`);
  - `ConnectPort 443` и `80`;
  - `Timeout 60`, `MaxClients 200`, `DisableViaHeader Yes`.
  Тот же список из трёх адресов стоит в nft на порт 3128.
- **Клиенты** ходят по `http://encar:<пароль>@<ip>:3128`, на практике только `CONNECT` на 443:
  - пять приложений на Habsida: encar-backend, encar, dongchedi, che168, dongchedi-login-service;
  - узел выбирают по кругу; после обрыва узел остывает 30 с, после бана — 15 мин.
- **cdn-pin** — systemd-таймер раз в 5 минут, `deploy/egress/cdn_pin.py`:
  - пишет в `/etc/hosts` блок закреплённых адресов CDN che168;
  - прокси должен видеть эти записи при каждом соединении;
  - файл заменяется атомарно (`os.replace`), то есть каждый раз появляется новый inode.
- **Узлы:**
  - узел 1 (136.234.5.122): nftables уже без `flush ruleset` (с 04.10); рядом работает glavdoroga на compose, её Caddy держит 80/443;
  - узлы 2–4: nftables с `flush ruleset`, порты 22, 3128 и больше ничего.
- **Плагин** `github.com/caddyserver/forwardproxy` @ `0aab84d` (2026-03-21) с Caddy v2.11.7
  через xcaddy собирается и работает (проверено на OrbStack 2026-10-07):
  - через прокси проходят `CONNECT` на HTTPS и обычный HTTP, исходящий адрес — адрес хоста;
  - назначение в приватной сети получает 403 (это ACL самого плагина, он ограничивает *назначение*, а не клиента);
  - клиент вне `remote_ip` получает отказ;
  - с `hide_ip`/`hide_via` заголовки о клиенте наружу не уходят;
  - открытый туннель переживает два `caddy reload` подряд: 4 MB скачались целиком, exit 0;
  - разницы в памяти со стоковым образом нет: 11 МБ против 57 МБ в простое (шум сборщика мусора);
  - образ весит 111 MB.

## Решения

Пересмотрены по ревью плана 2026-10-07 (`.runs/egress-plan-review.md`, свежий агент Claude; codex
недоступен до 10.10).

| # | Вопрос | Решение |
|---|---|---|
| E1 | Откуда forward proxy | Свой образ `boks-caddy`: `xcaddy build v2.11.7 --with github.com/caddyserver/forwardproxy@0aab84d`, база — `caddy:2.11.7-alpine`. Файлы: `proxy/Dockerfile`, тег в `proxy/TAG`. Собирает GitHub Actions на push в `proxy/`, push в GHCR. `DefaultProxyImage` закреплён по digest. Образ общий для всего парка: без `egress:` плагин ничего не делает. Работающие прокси обновляет `boks proxy upgrade` в удобное время, `proxy boot` до тех пор предупреждает о расхождении. Пакет публичный: его один раз переключает владелец |
| E2 | Где задаётся | В `server.yml`, блок `egress:`, применяется через `server apply` с ревизией. Поля: `port` (по умолчанию 3128); `allow` (CIDR клиентов, обязателен, `/0` запрещён); `user` и `password_env` (только вместе); `ports` (порты назначения, по умолчанию `[443]`; пулу encar — `[443, 80]`, как было у tinyproxy); `hosts_file` (E5) |
| E3 | Конфиг Caddy | Отдельный HTTP-сервер `egress` на `:<port>` с `automatic_https.disable`. Маршрут: `remote_ip` из `allow` → `forward_proxy` (`hide_ip`, `hide_via`, `allowed_ports`, `auth_credentials` = base64 от `user:password`, который JSON кодирует ещё раз), иначе 403. Журнала запросов нет. ACL плагина не трогаем: он запрещает приватные и loopback-цели. `dial_timeout` — 30 с, умолчание плагина. Отличия от tinyproxy: нет `MaxClients`, нет `Timeout 60`; недоступная цель даёт 403, а не 500 |
| E4 | Пароль | В `policy.json` и `history/` пароля нет. В `.boks/_server/egress.secret` (права 0600) лежит `user:password`. Секрет пишется до политики. Новый пароль ставится повтором `server apply` той же ревизии; сбой записи политики возвращает и прежний секрет. Откат берёт пароль из секрета на сервере, окружение не читает. Если у ревизии отката другой пользователь, откат отказывает на опросе всех серверов, до изменений: пароля этого пользователя на сервере нет, нужна новая ревизия с ним и его `password_env`. Каждый `server apply` файла с egress требует переменную с паролем (F14c): правку ботов boks от правки egress не отличает, а в файле пароля нет. Секрет пропал при политике с логином — деплои сервера отказывают (F14d): так задумано, конфиг без логина отдал бы 407 всем клиентам |
| E5 | `/etc/hosts` хоста | `hosts_file: <путь на хосте>` монтируется в `/etc/hosts` прокси через `--mount type=bind,readonly`: файла нет — Docker отказывает, а не создаёт каталог. Монтирование держит inode, поэтому писатели файла пишут на месте, а не заменой. cdn-pin переводится на запись на месте до переключения узла (правка в репо backends, шаг переключения). Go-резолвер замечает смену mtime и размера не чаще раза в 5 с; если он прочтёт файл ровно в момент записи, закреплений не будет до 5 с. `server status` сравнивает inode файла на хосте и внутри прокси и предупреждает о замене файла; лечит `docker restart boks-proxy`. Путь приводится к виду, в котором его записывает Docker (`path.Clean`), иначе форма не совпадала бы никогда и каждый `apply` пересоздавал бы прокси |
| E6 | Форма контейнера | Опубликованные порты (80, 443, порт egress) и монтирование `hosts_file` зависят от применённой политики (`proxy.Shape`). Все пути, которые создают прокси, берут форму из политики на сервере: `proxy boot`, `proxy upgrade`, `migrate`. `server apply` и `server rollback` сначала проверяют, что в работающем образе есть модуль `forward_proxy` и что `caddy validate` этим образом принимает новый конфиг. Если форма отличается, прокси пересоздаётся тем же образом той же подменой, что `proxy upgrade` (сбой — старый контейнер возвращается со старым конфигом), и только потом пишется политика и идёт reload. Снятие egress тоже меняет форму: прокси пересоздаётся без порта. Предпроверки — модуль `forward_proxy`, hosts-файл на месте, пароль для пользователя ревизии — идут при опросе всех серверов файла, до любых изменений (`proxy.CheckEgress`), и ещё раз перед остановкой. Если подмена прошла, а запись политики нет, контейнер остаётся в новой форме: повтор того же `apply` сходится, `server status` показывает расхождение |
| E7 | Совместимость | Формат фрагментов и маркер `_server.json` — `4` на всём парке: это константа `FragmentFormat`, как было с форматом 3. boks старее этой версии останавливается на любом сервере, где новый boks записал фрагмент или политику, а не собирает конфиг без egress и не пересоздаёт прокси без порта. Маркер «4 только с egress» отвергнут: фрагменты приложений пишутся тем же форматом, и условие пришлось бы протащить в каждый деплой. Следствие: boks обновляется везде, где его запускают, до первого запуска новой версии на сервере |
| E8 | Firewall | Порт, опубликованный Docker, проходит мимо input-цепочки хоста, и список nft на 3128 перестаёт действовать. Защита — `remote_ip` (как `Allow`) и basic auth: два слоя, оба на уровне HTTP, вместо трёх у tinyproxy. Сетевой фильтр в DOCKER-USER — вне этой работы. На узлах 2–4 `server install` откажет из-за `flush ruleset`: владелец сначала переводит nft на схему узла 1 |
| E9 | Узел 1 | glavdoroga держит 80/443 своим Caddy, поэтому `server install` там откажет. Узел 1 остаётся на tinyproxy, пока glavdoroga не переедет под boks (отдельная работа) |

  - `hosts_file` при записи на месте виден без перезапуска;

  - перезагрузка машины — egress снова отвечает

    `boks server status`: строка о заменённом hosts-файле значит, что писатель всё ещё меняет inode;
  - nft по схеме узла 1: правило на 3128 в input после переключения мёртвое (Docker обходит input),
    его удаляют; 80/443 на узлах 2–4 впервые отвечают миру (Caddy, 404) — принятое следствие (F9);
  - до канарейки проверить, как клиенты считают CONNECT 403 от прокси (недоступная цель): если как
    бан узла, поставить `dial_timeout` и сверить с бюджетом попытки che168 8 с (F11);
  - канарейка: узел 2 на 3129 рядом с tinyproxy, Habsida шлёт часть запросов; критерий «здоров» и окно
    наблюдения назначает владелец при переключении (F5d) — в этой работе их нет;
  - затем узлы 2–4 по одному, `server.yml` на один узел: nft по схеме узла 1, `server install`, `systemctl disable --now tinyproxy && systemctl mask tinyproxy`, `server apply` на 3128;
  - откат узла: `server rollback` на ревизию без egress, `systemctl unmask tinyproxy && systemctl enable --now tinyproxy`;
  - узел 1 — после glavdoroga

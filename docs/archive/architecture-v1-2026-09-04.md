# boks — заметки по архитектуре

Статус: ранняя стадия обсуждения дизайна, реализации ещё нет. Этот документ — снимок решений,
принятых на данный момент, вместе с обоснованием каждого, чтобы дальнейшей работе (человеку или
LLM) не пришлось заново это выводить.

## Что это

boks — self-hosted платформа для деплоя, призванная заменить [Dokploy](https://dokploy.com) на
серверах Habsida-org. Причина заменить, а не латать — избыточное потребление ресурсов: Dokploy
грузит в память много ненужного просто чтобы работать. Цель — сервис, который комфортно
работает на минимальной конфигурации сервера.

## Руководящий принцип дизайна

**Нет пользователей без LLM.** boks проектируется в явном предположении, что у любого
пользователя есть доступ к LLM. Раз любая современная LLM умеет писать Dockerfile, boks не
проектируется под тех, кто этого не умеет — это не узкое ограничение «только для Евгения», а
постоянное правило оценки любой будущей фичи. Вопрос для любой фичи вида «сделать удобнее для
пользователя» — не «нужно ли это новичку», а «может ли пользователь с LLM сделать это сам без
нашей фичи». Большинство удобств/подстраховок для новичков этот тест не проходят. Этим же
объясняется выбор CLI/API-first вместо полированного UI-мастера: пользователь с LLM спокойно
работает напрямую через CLI или API.

## Ядро

- **Язык: Rust.** Статический бинарник, низкий RSS, тот же класс инструмента, что Caddy/Traefik/
  k3s. (Изначально был Go — переключились на Rust специально ради того, чтобы reverse proxy на
  базе Cloudflare Pingora можно было встроить в тот же процесс, а не городить отдельный sidecar
  или cgo FFI-мост. См. «Reverse proxy» ниже.)
- Ядро и UI — раздельные, независимые модули, не одно приложение. Ядро headless и отдаёт API; UI
  — тонкий клиент этого API. Отсюда же и естественность CLI/API-first для работы с ядром, а не
  отдельный компромисс.
- **Топология: без обязательного центрального control-plane.** Каждый сервер держит свой
  независимый инстанс ядра. UI может подключаться к одному инстансу или сразу к нескольким для
  единого multi-server обзора — агрегация происходит на стороне UI, не в тяжёлом центральном
  демоне. Это убирает единую точку отказа и держит footprint каждого сервера равным footprint'у
  его собственного ядра. Подтверждено по факту: все 4 сервера Habsida-org уже сегодня работают
  полностью независимо (без кластеризации через Docker Swarm) — это не новое ограничение, оно
  совпадает с тем, как инфраструктура уже устроена.
- Контейнерный рантайм остаётся **Docker Engine** — не containerd напрямую, не Podman, не
  nerdctl. На этих серверах Docker уже обслуживает существующие нагрузки; менять рантайм —
  рисковать тем, что и так работает, ради выигрыша меньше, чем кажется (собственный idle RSS
  демона Docker, ~30-80MB, — не то, откуда на самом деле берётся bloat Dokploy — это его
  Node/NestJS-слой + связка Postgres/Redis/Traefik + дашборд). Говорить с Docker через его Engine
  API с помощью `bollard`, не шеллом на `docker` CLI. containerd напрямую рассматривался (он и так
  уже крутится под установленным Docker, новая установка не нужна), но экосистема Rust-клиентов
  под прямой доступ к containerd незрелая — Docker Engine API через `bollard` практичнее по
  умолчанию.

## Слой данных

**Postgres на всё — один общий инстанс на сервер.** Не SQLite, не отдельный Postgres-контейнер
на каждое приложение. Это заменяет:
- Redis → unlogged-таблицы Postgres, под кэш/сессии — состояние, которое не страшно потерять
  при краше.
- Cron → `pg_cron`.
- Разрозненное хранилище конфигов → колонки `JSONB`.
- Очереди задач → расширение [`pgmq`](https://github.com/pgmq/pgmq) (семантика в духе SQS:
  send/read/delete/archive, visibility timeout для безопасной повторной доставки). Отдельный
  случай от unlogged-таблиц: таблицы очередей PGMQ — обычные, **логируемые**, потому что очередь
  сборок/вебхуков обязана пережить краш — в отличие от кэша, терять её нельзя. Это напрямую даёт
  сериализацию сборок (ниже) как готовый примитив, а не что-то, что нужно писать руками.

Приложения, задеплоенные через boks (дилерские сайты, бэкенды и т.д.), подключаются к тому же
общему инстансу Postgres, изолированные по приложению через **схемы Postgres**
(`app_name.users`, не префиксы в именах таблиц). Схемы выбраны вместо префиксов, потому что дают
бесплатную нативную инструментовку: `pg_dump -n schema_name` бэкапит/восстанавливает одно
приложение изолированно, а `GRANT ... ON SCHEMA` даёт изоляцию доступа на уровне SQL.

**Foreign key через границу схем приложений запрещены.** Приложения остаются логически
изолированными, интеграция только через API/события — разрешить FK через схемы значило бы
сломать ту самую изоляцию, ради которой схемы и выбирались (нельзя восстановить приложение A
изолированно, если оно ссылается на строки приложения B; нельзя удалить B, пока на него
ссылается A). Если возникнет по-настоящему общая сущность (например, каталог марок/моделей
машин для нескольких дилерских сайтов) — ответ явная **shared-схема**
(например `shared.car_models`), на которую приложения объявляют зависимость — осознанная,
видимая часть общей инфраструктуры, а не случайная связанность. Ядру нужно будет отслеживать,
какие приложения зависят от каких shared-схем, чтобы такая схема не удалилась, пока на неё ещё
ссылаются (пока не спроектировано).

**Осознанно принятый компромисс:** один общий процесс Postgres означает общие WAL, checkpointer,
autovacuum, `max_connections` и, что важнее всего, общий MVCC xmin horizon — зависшая сессия
`idle in transaction` в одном приложении может заблокировать vacuum для всех приложений на этом
сервере. Это было проверено против альтернативы (отдельные database в одном инстансе) и
альтернатива не оказалась лучше: реальная граница изоляции в Postgres — это инстанс, а не
database — WAL один на весь кластер, не по database, и xmin horizon общий на инстанс в любом
случае. Отдельные database дали бы только изоляцию расширений по database, ценой потери
нативных join'ов между схемами. Так что схема на приложение подтверждена как правильный выбор,
а не компромисс. От ядра ожидается выставлять лимиты на роль при провижининге, чтобы это
компенсировать: `CONNECTION LIMIT`, `statement_timeout`, `idle_in_transaction_session_timeout` —
плюс мониторинг возраста транзакций на уровне всего инстанса, а не только по отдельной схеме.

**Заметка про миграцию:** сегодня реальное использование на 4 серверах — это ~12 one-click
Postgres-контейнеров и ~11 one-click Redis-контейнеров, по одному на приложение — ровно тот
паттерн, который этот дизайн заменяет. boks нужен реальный путь миграции для них, не только
дизайн с чистого листа. Это частично уже снято с рисков: 7 из 8 Convex-приложений в выборке
из аудита compose-файлов (см. ниже) уже были **вручную мигрированы** на общий внешний
Postgres-инстанс ещё до появления boks — то есть процесс миграции в основном нужно записать и
автоматизировать, а не изобретать с нуля.

## Reverse proxy / TLS

**[Pingora](https://github.com/cloudflare/pingora), встроенный прямо в процесс ядра** (через
Tokio) — не отдельный процесс. Важно: Pingora — это *фреймворк* для построения прокси, не
готовый продукт вроде Caddy/Traefik: автоматического ACME/HTTPS/hot-reload из коробки нет, это
строится поверх. Именно это стало причиной смены языка ядра на Rust — Rust-прокси внутри
Go-ядра потребовал бы sidecar-процесса или cgo-моста; внутри Rust-ядра это просто ещё один
crate.

**Поддержка ACME DNS-01 (wildcard-сертификат) обязательна для v1, не опциональна.** Один из 4
серверов уже сейчас реально зависит от DNS-01 через Selectel DNS для wildcard-сертификата.
Встроенный ACME-клиент обязан поддерживать DNS-01, не только HTTP-01, с самого начала — это
делает категорию плагина «DNS provider» обязательной для v1, а не приятным дополнением.

Собственный control API ядра отдаётся как ещё один virtual host на том же инстансе Pingora — см.
«UI ↔ ядро» ниже.

## Модель деплоя

**Только Dockerfile.** Ни автодетект сборки в стиле Nixpacks, ни поддержка docker-compose. Оба
рассматривались и отклонены — обоснование ниже — но решение подтверждено по реальному
содержимому compose-файлов на всех 4 серверах, а не оставлено на одних рассуждениях от первых
принципов.

Два случая источника деплоя явно входят в scope сверх обычной сборки по Dockerfile, оба
подтверждены необходимыми после чтения реальных compose-файлов:

1. **Деплой уже собранного, запиненного образа — без шага сборки.** Большая часть найденного в
   аудите использования compose вообще ничего не собирает, а просто пиннит уже собранный образ
   (например `ghcr.io/get-convex/convex-backend:<sha>`) из приватного registry. Это должно быть
   полноценным режимом деплоя наравне со «сборкой из Dockerfile».
2. **Несколько экспонируемых портов на одно приложение, каждый маршрутизируется независимо на
   свой домен/TLS.** Например, бэкенду нужны отдельные роутируемые домены для порта client-API и
   порта HTTP-actions. Собственный Application-ресурс Dokploy через UI это не умеет выразить —
   именно это, а не bundling нескольких сервисов, реально толкало людей в compose.

### Почему Nixpacks отклонён

Решает проблему «пользователь не хочет писать Dockerfile» — не наша проблема: каждое приложение,
которое деплоит boks, Евгений и так контролирует и может свободно добавить туда Dockerfile.
Написание и поддержка эвристик автодетекта — постоянные расходы ради проблемы, которой у
реальных пользователей этого проекта нет. Подтверждено аудитом: ноль использования
Nixpacks/buildpacks/static-сайтов на всех 4 серверах сегодня. Если boks когда-нибудь станет
обслуживать внешних пользователей, это можно добавить позже как плагин/внешний вызов — при
откладывании ничего не теряется.

### Почему docker-compose отклонён

Реальная дополнительная сложность по четырём независимым осям: (1) корректный парсинг
достаточного подмножества Compose Specification (интерполяция переменных, `depends_on` с
healthcheck, profiles, слияние нескольких файлов) — реальный объём работы; (2)
multi-container-на-приложение требует новой сущности «app unit» для порядка передеплоя/рестарта,
которая не нужна при чистой модели «один контейнер — одно приложение»; (3) прокси должен знать,
какому из N сервисов в compose-файле отдавать публичный трафик, а нативного понятия для этого в
Compose нет; (4) реальные compose-файлы по традиции объявляют свои `postgres`/`redis`-сервисы,
что прямо конфликтует с решением про общую Postgres — поддерживать это добросовестно значит либо
молча выкидывать часть файла пользователя, либо отклонять его, то есть незаметно поддерживать
урезанный диалект под видом совместимости.

Это решение **ненадолго переоткрывалось** после того, как живой аудит нашёл 26 реально
используемых compose-ресурсов (18 на самом нагруженном сервере) — и было **подтверждено заново**
после чтения реального YAML по репрезентативной выборке. Находки: только 1 из 15 файлов в
выборке реально bundling'ит свою Postgres (явный кандидат на миграцию, не контрпример);
единственный по-настоящему многосервисный случай — стек Prometheus/Grafana для наблюдаемости,
который является инфраструктурой платформы, а не клиентским приложением, и полностью вне scope
boks. Два реальных драйвера использования compose — это как раз два случая источника деплоя
выше, и ни один не требует полной Compose Specification.

## Архитектура плагинов

boks остаётся минимальным, не встраивая интеграции (VCS-провайдеры — GitHub/GitLab/Bitbucket/
Gitea — нотификаторы, DNS-провайдеры, бэкенды хранилища бэкапов) напрямую в ядро; они приходят
как плагины. «Плагины могут добавлять любую функциональность» на практике означает несколько
типизированных интерфейсов точек расширения по категориям (VCS provider, notifier, DNS provider,
storage backend) плюс общие lifecycle-хуки (pre-deploy, post-deploy, on-webhook, on-app-created)
— не один универсальный интерфейс «делай что угодно». Смоделировано по тому, как Kubernetes
разделяет CSI/CNI/admission-webhooks/контроллеры вместо единого plugin API; универсальный
интерфейс «делай что угодно» пришлось бы наделять доступом почти ко всем внутренностям ядра, что
сводит на нет смысл изоляции плагинов вообще.

**Механизм: subprocess + RPC**, паттерн, который популяризировал `go-plugin` от HashiCorp
(используется в Terraform, Vault, Consul, Packer) — переизобретён поверх `tonic` (gRPC-фреймворк
для Rust), а не через зависимость от (Go-специфичного) пакета `go-plugin`. Нативная загрузка
динамических библиотек ОС (`.so`/`dlopen`) отклонена: у Rust нет стабильного ABI между версиями
компилятора для этого — возможно, даже хуже, чем у ныне заброшенного пакета `plugin` в Go.
Выбрано вместо WASM, потому что VCS-плагинам нужен исходящий HTTP к API провайдеров, который
subprocess получает бесплатно, а WASM потребовал бы прокладывать host-функции. Если WASM-песочница
когда-нибудь понадобится для ужесточения — естественный рантайм это `wasmtime` (нативный Rust
API, никакой FFI-границы, в отличие от `wazero`/`wasmtime-go` из Go-экосистемы).

**Модель доверия:** любой может написать и установить свой плагин на свой сервер — self-hosted
значит self-trust, никакого удалённого/автоматического push плагинов нет. Проект ведёт один
курируемый список плагинов как сигнал доверия; это отдельный вопрос реестра/каталога, не часть
модели исполнения. Раз установка плагина — всегда осознанное действие владельца сервера,
изоляции на уровне процесса достаточно для v1.

**Пока не спроектировано:** конкретная таксономия точек расширения плагинов и форма RPC-контракта.
Категории выше — начальный набросок, не готовый интерфейс.

## UI ↔ ядро: транспорт и аутентификация

**Обычный HTTPS API + bearer-токен.** (SSH-туннелирование рассматривалось первым и было
отклонено — см. ниже, оставлено в записи, потому что в эту ловушку легко вернуться снова.)

- Control API ядра отдаётся как ещё один virtual host на том же встроенном инстансе Pingora,
  который уже обслуживает задеплоенные приложения — переиспользуя его ACME/TLS-механику вместо
  отдельной истории.
- Аутентификация — bearer-токен (`Authorization: Bearer ...`), генерируется при первом запуске
  ядра, ротируемый/отзываемый — стандартный паттерн API-ключа (ср. personal access token в
  GitHub).
- UI хранит `{url, token}` на инстанс (в духе Docker context/kubeconfig) и делает прямые,
  параллельные HTTPS-запросы к каждому отслеживаемому серверу — никаких туннелей, никакой
  возни с локальными портами.
- Опрос нескольких инстансов идёт параллельно без межсерверной координации, что совпадает с
  топологией «без центрального control-plane». Каждое подключение к серверу должно иметь своё
  состояние connect/reconnect-с-backoff и свой индикатор статуса в UI — один недоступный сервер
  никогда не должен блокировать или ронять отображение остальных.

**Почему SSH-туннелирование отклонено как вариант по умолчанию:** изначально предлагалось из
рассуждения, что ядру «никогда не нужно быть публичным» (слушать только localhost, UI поднимает
туннель на сервер через `russh`). Эта посылка не держится: ядро и так обязано принимать входящие
вебхуки от GitHub/GitLab/etc. по архитектуре плагинов — а это требование входящего публичного
HTTP, которое никакой SSH-туннель, инициированный UI, удовлетворить не может. Раз ядру в любом
случае нужен публичный HTTPS-эндпоинт, нет смысла давать UI ещё и отдельный SSH-канал.
SSH-туннелирование остаётся доступным как опциональный альтернативный транспорт для тех, кто
хочет нулевой публичной доступности и готов пожертвовать webhook-триггерами деплоя (переходя на
polling) — но не по умолчанию.

## Выбор крейтов реализации

- **Git-операции:** [`gitoxide`/`gix`](https://github.com/Byron/gitoxide) — чистый Rust, без
  FFI-моста, согласуется с уже принятой позицией «без cgo» для слоя прокси. Принятый риск: не
  100% совместимость по фичам git (LFS и некоторые edge case ещё дозревают). Рассмотрены и
  отклонены: `git2-rs` (libgit2 через FFI — проверенно, но не чистый Rust) и шелл на системный
  `git`.
- **Postgres-клиент:** [`sqlx`](https://github.com/launchbadge/sqlx) для собственных
  хорошо определённых таблиц control-plane ядра (состояние деплоев, метаданные приложений,
  реестр плагинов — фиксированная схема, где проверка запросов на этапе компиляции окупается).
  Динамический DDL для провижининга схем приложений (`CREATE SCHEMA`, `GRANT` и т.д.) в любом
  случае идёт как raw SQL, поскольку compile-time проверка не применима к схемам, которых ещё не
  существует на момент сборки. Рассмотрен и отклонён: `tokio-postgres` + `deadpool-postgres`.

## Находки аудита реального использования Dokploy (2026-09-04)

Живой, read-only аудит реального Dokploy API на всех 4 серверах Habsida-org
(Habsida/Office/Bravo/Shchr), сделанный специально, чтобы обосновать решения по scope реальным
использованием, а не догадками.

**Подтверждённо не используется — можно безопасно не строить:** MySQL/MariaDB/MongoDB (только
Postgres+Redis, ноль инстансов чего-либо ещё). Мультисерверная кластеризация через Docker Swarm
(все 4 сервера полностью независимы). Marketplace/templates. Команды/RBAC/организации (всегда
один admin API-ключ на сервер). Nixpacks/buildpacks/static-сборки. Собственный CLI Dokploy (вся
реальная работа и так идёт через API напрямую).

**Подтверждённо используется, но уже заменено на что-то лучшее — не стоит строить хуже:**
- Встроенные графики CPU/RAM в Dokploy мертвы; команда уже держит отдельный стек
  Prometheus+Grafana+Loki+Alloy+cadvisor+node-exporter, потому что встроенных графиков не хватало.
  **boks не должен строить конкурирующий дашборд метрик** — отдавать статистику в формате,
  который existing Prometheus сам заберёт (эндпоинт `/metrics`), а не городить свой UI.
- Встроенные уведомления Dokploy (Slack/Discord/Telegram/email) тоже мертвы, заменены
  собственными Telegram-скриптами алертинга (courier, cert-monitor, redis-cap-guard). Это прямо
  подтверждает категорию плагина «notifier» как конкретную, не гипотетическую цель замены.

**Новые требования, которые это форсирует, ранее не обсуждавшиеся:**
- **Сериализация сборок обязательна по умолчанию на серверах с ограниченными ресурсами.** Bravo
  и Shchr сейчас требуют вручную настроенного systemd timer поверх Dokploy для принудительной
  последовательной сборки, иначе конкурентные сборки топят бокс. Ядро не должно полагаться, что
  оператор сам прикрутит это снаружи, как пришлось для Dokploy — `pgmq` даёт это готовым
  примитивом (см. «Слой данных»).
- **Деплой уже собранного образа из registry без шага сборки** — см. «Модель деплоя» выше.
- **Несколько экспонируемых портов на приложение, независимо маршрутизируемых** — см. «Модель
  деплоя» выше.
- **Поддержка ACME DNS-01/wildcard обязательна, не опциональна** — см. «Reverse proxy» выше.

**Известные баги корректности Dokploy, которые не стоит повторять** (реальные продакшен-инциденты,
не недостающие фичи): триггер деплоя не гарантирует, что пересборка реально произошла (пришлось
проверять через отдельный список деплоев); preview-деплой может пересобраться из устаревшего
чекаута без повторного клонирования; пересоздание preview может осиротить его старый Swarm-сервис
(потребовало написанной вручную cron-уборки); автопродление SSL может молча не срабатывать
месяцами без встроенного алертинга; и, важнее всего — **API Dokploy отдаёт секреты (переменные
окружения, пароли от registry) целиком в теле ответа на мутации.** Собственный API boks не должен
никогда отдавать значения секретов обратно в ответах: только write-only поля, маскированные/
скрытые при чтении.

**Не подтверждено:** привязаны ли реально существующие R2 (S3-совместимые) креды в хранилище
секретов к фиче бэкапов Dokploy для инстансов Postgres/Redis, или используются как-то иначе.
Нужна дополнительная проверка, прежде чем считать, что boks нужно воспроизводить уже работающий
поток бэкапов, а не строить его с нуля.

## Открыто / пока не решено

- Путь миграции оставшихся per-app контейнеров Postgres/Redis в модель общего инстанса + схем
  (частично снято с рисков, см. «Слой данных» выше).
- Механизм бэкапов Postgres/Redis (использование R2 не подтверждено).
- Конкретная таксономия точек расширения плагинов и форма RPC-контракта — нужна реальная
  проектная работа, не быстрое решение.

## О масштабе и темпе

Это полный переписывание PaaS-платформы (свой control-plane, встроенный reverse proxy с ACME,
система плагинов, UI, миграция слоя данных с нуля для инфраструктуры, которая уже обслуживает
живой трафик) — реалистично это долгий проект, не выходные. Стоит держать раздельно два риска:
время, которое уйдёт на то, чтобы код вообще заработал, и риск миграции того, что *уже*
обслуживает реальный продакшен-трафик (дилерские сайты) — с работающей сегодня системы на новую.
Естественная защита от этого — не big-bang переключение: держать Dokploy работающим, новые или
некритичные нагрузки сразу отправлять в boks, а то, что уже приносит деньги, переводить только
когда boks реально доказал себя на практике.

Соответственно маленькая первая веха: ядро умеет ровно одно — принять запрос на деплой,
склонировать репозиторий через `gix`, собрать `docker build` из его Dockerfile через `bollard`,
провижинить схему в Postgres, запустить контейнер и отдать его через встроенный Pingora с
настоящим сертификатом. Без плагинов, без UI (curl/CLI достаточно, чтобы это проверить), без
миграции существующих баз данных — просто доказательство, что вся цепочка работает, на одном
некритичном приложении.

## Ревизия 2026-09-05 — критический разбор и вердикты

Документ выше прошёл критический разбор (внешние рецензенты: codex — упёрся в лимит до
7 сентября; grok — исключён из обсуждения по решению автора). Ниже вердикты по пунктам.
**Разделы выше пока не переписаны** — консолидация после обсуждения build-vs-buy, потому что
от него зависит, что именно строим и на каком языке.

Уточнение цели: мы не используем дешёвые серверы с малым RAM именно потому, что накладные
расходы Dokploy для них слишком велики (измерено: control-plane Dokploy ≈1 GB на Bravo с 5.8 GB
и хроническим memory-pressure; Shchr сознательно ужат до 2 vCPU / 4 GB). Задача boks — сделать
дешёвые серверы пригодными. Реальные замеры `docker stats`/`free` по серверам запущены.

### Принято, меняет фундамент

- **Database на приложение вместо схемы на приложение** (одна общая инстанция на сервер). Правило
  «без FK между приложениями» запретило единственное, что схемы дают сверх database. Database даёт
  ту же изоляцию (`pg_dump dbname`, `DROP DATABASE`, `GRANT CONNECT`), плюс изоляцию расширений,
  плюс совместимость с приложениями: self-hosted Convex берёт URL базы и владеет ею целиком —
  несколько Convex-бэкендов в одной database столкнутся; «7 из 8 уже мигрировали на общий инстанс»
  почти наверняка означает общий инстанс + отдельные database. Footprint тот же (граница изоляции
  — инстанс). Preview-окружения получают `CREATE DATABASE preview_x TEMPLATE app_db`. Гипотетическая
  `shared.*`-схема снимается. Раздел «Слой данных» подлежит переписыванию.
- **Плагинная система откладывается за пределы v1.** Три интеграции одного автора (GitHub-вебхук,
  Selectel DNS-01, Telegram) не оправдывают subprocess + gRPC + handshake. v1 — compile-time
  features (Cargo features или эквивалент), чтобы неиспользуемые интеграции не попадали в
  бинарник. Возвращается, когда появится второй автор плагинов.
- **Сборка вне app-серверов по умолчанию**: app-сервер только тянет запиненный образ из registry.
  Оговорка: должна быть возможность настроить **отдельный собственный build-сервер** (не только
  GitHub Actions/Depot). Следствия: роль «builder», registry (свой или внешний), требование
  сериализации сборок на слабом боксе в основном исчезает. Сборка из Dockerfile на app-сервере —
  вторичный путь.
- **Redis исключён полностью, включая приложения.** Приложения обязаны следовать тому же паттерну
  «всё в Postgres». Это требование к приложениям, а не только к ядру; существующие боты на Redis
  переделываются при миграции.
- **Loki — обязательный элемент платформы для логов**, может бежать на другом инстансе. Ядро логи
  не хранит, только отправляет (через Alloy или Loki push). Та же позиция, что по метрикам.
- **Pingora больше не аргумент за Rust.** Критика принята: TLS-бэкенд Pingora по умолчанию —
  OpenSSL/BoringSSL через FFI (противоречит правилу «без FFI», по которому отвергли `git2-rs`;
  `pingora-rustls` моложе), а ACME с продлением, hot-reload маршрутов, WebSocket/HTTP2 и
  multi-port routing поверх него — это переписывание ядра Caddy, причём продление — ровно то,
  что молча ломалось у Traefik месяцами. **Вопрос языка и прокси возвращается в открытые и
  решается после build-vs-buy.** «Хотим Rust» — легитимная причина сама по себе; «нужен Pingora» —
  нет.

### Принято, добавляется в дизайн (разделы будут написаны)

- Zero-downtime деплой (новый контейнер → health check → переключение upstream → drain → стоп
  старого) и rollback с хранением последних N образов. Сейчас серверы в Swarm-режиме — переход на
  plain containers меняет семантику рестартов и обновлений.
- Preview-окружения на PR: свой домен (отсюда wildcard и DNS-01), своя database (TEMPLATE от prod
  или пустая — решить), teardown при закрытии PR, сборка осиротевших.
- Обновление самого boks без падения прокси (fd-passing / socket handoff — единственное, в чём
  Pingora была по-настоящему хороша; замена обязана уметь то же).
- Безопасность API: токен хранится хэшем; scope/expiry/rate-limit/IP-allowlist/audit log;
  вебхуки проверяются своей HMAC-подписью отдельно от bearer-токена.
- Свой образ Postgres с pgmq/pg_cron/pgcrypto — поддерживаемый артефакт (pg_cron требует
  `shared_preload_libraries` и живёт в одной database).

### Отвергнуто

- «UI нельзя откладывать из-за Office» — Office выводится из эксплуатации полностью (без SSH
  слишком много проблем). UI остаётся после v1. Парк: Habsida, Bravo, Shchr (+ Tokyo/OCI вне
  аудита).

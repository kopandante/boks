## Что это и зачем

boks заменяет [Dokploy](https://dokploy.com) на серверах Habsida-org. Причина измерена, а не
предположена: control-plane Dokploy — это один Node-процесс на 780–900 MB, одинаковый на любом
боксе; на Shchr (4 GB) это 22% RAM, на Bravo (6 GB) 16%. Именно из-за этих накладных расходов
дешёвые серверы с малым RAM сейчас не используются — задача boks сделать их пригодными.
Удаление этого процесса экономит 760–900 MB на сервер; всё остальное (консолидация баз, Redis)
даёт операционный, а не памятный выигрыш.

## Руководящий принцип

**Нет пользователей без LLM.** Любая LLM умеет писать Dockerfile, конфиг и CLI-команды — boks
не проектируется под тех, кто этого не может. Фильтр для любой фичи «сделать удобнее»: сможет
ли пользователь с LLM сделать это сам. Отсюда CLI-first: UI и агент приходят к серверу через тот же control API, своих облегчённых
путей у них нет (см. «Control API, UI и агент»).

## Форма решения

**boks — тонкий оркестратор-CLI на Go**, который живёт на ноутбуке, в CI и на build-сервере и
по SSH управляет Docker и прокси (Caddy) на app-серверах. **Критерий — минимальный футпринт на
сервере** (формулировка автора, 2026-09-15). Сегодня постоянно работающего процесса boks там нет;
по решению той же сессии появится один — `boksd` (см. «Control API, UI и агент»). Критерий — не
запрет класть на сервер что-либо своё: бинарник, который запускается по таймеру и между запусками
не занимает ничего, футпринту не противоречит. Свой след у boks на сервере и сейчас есть —
контейнер `boks-proxy`, сеть, тома `boks-proxy-data` и `boks-certs`, лейблы контейнеров,
env-файлы, отметки о загрузке сертификата, снимки релизов и журнал операций в `.boks/<app>/`
(с PR #37), фрагменты маршрутов и применённый конфиг прокси в `.boks/_proxy/`. Постоянно живут на сервере только:

| Компонент | Что делает | RSS |
|---|---|---|
| Docker Engine | контейнеры (plain containers, не Swarm) | ~110 MB (dockerd, измерено на пустой машине) |
| [Caddy](https://caddyserver.com) 2.11.7 | host-routing, TLS (ACME и файлы), reload без потерь при `tcp_migrate_req=1`, drain старого сервера | **46 MB RSS в простое, 74 MB пик** под 20 TLS-хостами (измерено 2026-10-06; kamal-proxy v0.10 на том же стенде — 18 / 36 MB) |
| Postgres (один инстанс, свой образ) | базы всех приложений + pgmq/pg_cron/pgcrypto для них | по рабочему набору |
| Alloy | доставка логов в Loki на другом инстансе: читает json-file контейнеров (boks задаёт его явно — приложениям 3 × 10 MB, прокси 5 × 10 MB, B5) | небольшой |
| `boksd` — control API | вход для UI и агента, mTLS | единицы MB, **замерить на стенде** |

Почему так, а не иначе (коротко; подробно в `build-vs-buy.md`):
- **Не Kamal-gem**: Ruby в тулчейне, и абстракция «одно приложение = один target» мешает
  кейсу «два порта одного контейнера под двумя доменами». kamal-proxy, самостоятельный Go-инструмент,
  был прокси boks до 2026-10-06; Caddy заменил его ради заголовков, путей и фильтров, за +30–40 MB.
- **Не Dokku**: nginx, сборка на сервере по умолчанию, `config:show` печатает секреты.
- **Не Uncloud**: демон + CRDT-состояние + WireGuard-кластер, 100–200 MB.
- **Не свой Rust-демон с Pingora и плагинами** (v1): весь выигрыш — убрать Node-процесс, и
  kamal-proxy убирает его так же полно; всё остальное из v1 было либо переписыванием Caddy
  (ACME с продлением, hot-reload), либо машинерией масштаба Terraform (плагины) для одного
  автора и трёх интеграций.
- **Go, а не Rust**: язык теперь свободен от Pingora; для тонкого CLI важнее экосистема —
  Docker-клиент, ssh, kamal-proxy написаны на Go; один статический бинарник для ноутбука и CI.

## Почему не Swarm

Вопрос автора 2026-09-15 вскрыл пробел: решение «plain containers, не Swarm» стояло в документе
строкой таблицы, без единого довода. Названо было другое — аудит 2026-09-04 записал в
«подтверждённо не используется» **мультисерверную кластеризацию** (все серверы независимы, кластера
нет). Dokploy же держит Swarm не ради кластера, а ради абстракции сервиса на одной машине. Из
«кластер не нужен» молча получилось «Swarm не нужен».

**Что Swarm даёт даром** (проверено по коду Dokploy, `utils/docker/utils.ts` и
`utils/databases/*.ts`): `UpdateConfig {Parallelism 1, Order start-first, FailureAction rollback}`
для приложений и `Order stop-first` для баз; прежняя спецификация сервиса хранится в raft, поэтому
откат не требует своей памяти о релизах; плюс рестарт-политики и secrets. В нашем бэклоге это
задачи #13 (журнал релизов), #14 (откат по снимку) и #24 (режимы замены).

**Почему всё же простые контейнеры:**

- **наблюдаемость.** Для cAdvisor обновление сервиса неотличимо от падения: Swarm гасит старую
  задачу и поднимает новую. Из-за этого пришлось писать свой `swarm-exporter`, а myencar загорелся
  tier-0 при одиннадцати здоровых деплоях за 26 минут;
- **дублирование.** boks сам ждёт health-check и переключает трафик одним reload прокси — ровно
  та работа, ради которой держат Swarm-сервис;
- **журнал релизов нужен всё равно** — для аудита, секретов релиза и доведения операции после
  обрыва связи, а не только ради отката. Даром он не достался бы и в Swarm.

**Цена решения названа явно:** три задачи бэклога делают руками то, что оркестратор давал
бесплатно. Решение обратимо: если журнал релизов окажется дороже ожидаемого, возврат к
Swarm-сервисам — честная альтернатива, а не поражение.

## Модель деплоя

**Только Dockerfile.** Без Nixpacks и без docker-compose — подтверждено чтением реальных
compose-файлов: они использовались ради готовых образов и multi-port, а не ради multi-service.

**Сборка вне app-серверов.** Образ собирается на build-сервере (настраиваемый: свой хост через
`docker context`/buildx over ssh, или GitHub Actions/Depot как сейчас) и кладётся в registry.
**Реестр по умолчанию — Depot** (автор, 2026-10-02: «Сборки через Depot»): `depot build --save
--save-tag <sha>` кладёт образ в реестр проекта `registry.depot.dev/<project>` (проверено
2026-10-04, #52; не `<org>.registry.depot.dev`); образы `--save` хранятся бессрочно, пока политика
хранения проекта Depot стоит на значении по умолчанию «Unlimited» (при сроке короче `keep` и откат
потеряют релизы старше срока). Вход в реестр (E2) объявляется в `boks.yml` блоком
`registry: {host: registry.depot.dev, token_env: DEPOT_TOKEN}` (`user` по умолчанию `x-token`);
самого токена в конфиге нет. Токен — общий токен Depot (владелец, 2026-10-04: «Токен общий на все
проекты cars»; короткоживущий `depot pull-token` для реестра проекта отвечает `not_found`, #52) —
boks берёт из окружения машины, где запускается (оболочка оператора или CI, туда он приходит из
bws); объявленный, но не заданный токен — отказ до первого обращения к серверу (E6). На сервере
login, pull и logout идут одним скриптом под тем же пользователем и с тем же docker-конфигом:
`docker login <host> -u x-token --password-stdin` (токен только в stdin, не в аргументах — их видно
в `ps`), `docker pull`, `docker logout <host>` по ловушке `EXIT`, взведённой до login, — то есть при
успехе, ошибке, сигнале и обрыве связи с boks. Pull идёт в фоне под наблюдателем: раз в 2 с тот пишет
в соединение и, если запись не прошла, останавливает pull — молчащий pull иначе не узнал бы об
отмене. Входы сериализуются `flock` на `boks.registry.lock` в каталоге docker-конфига
(`${DOCKER_CONFIG:-~/.docker}`): конфиг у приложений сервера общий, и logout одного деплоя иначе
попал бы между login и pull другого. Pull идёт до загрузки прокси, так что отвергнутый токен — отказ до изменений на сервере.
Реестр по HTTP не поддерживается: `http://` и loopback отвергаются в конфиге, а перед отправкой
токена boks спрашивает у docker сервера (`docker info`), не числится ли хост в insecure-registries
или в небезопасных диапазонах. Контейнер приватного образа запускается с `--pull never`: образ
приносит только этот pull. Постоянных учётных данных реестра на сервере нет.

App-сервер только `pull`. Сборка на app-сервере — не режим v1; если понадобится — с
принудительной сериализацией. Важно для ARM-боксов (OCI): образ должен
быть multi-arch — `docker manifest inspect` до деплоя.

**Поток `boks deploy app@tag`** (с Caddy, 2026-10-06; замеры — `plans/20261006-caddy.md`):
1. `docker pull` образа с тегом на сервере.
2. Запуск нового контейнера (`<app>-<tag>-<unix>`, лейблы: app, version, ports, replace) в сети
   `boks-<app>`; прокси подключается к ней, если ещё не там.
3. Опрос здоровья каждого порта **из контейнера прокси** по имени новой копии: `wget` на
   `health_path` (по умолчанию `/up`, как у kamal-proxy) и `health_port` (по умолчанию сам порт),
   5 с на попытку, в пределах `deploy_timeout`. Для порта без 2xx-эндпоинта (у Convex — 3211) health
   проверяется через другой порт того же контейнера (`health_port: 3210`, `health_path: /version`).
   Не ответила — копия удаляется, маршрутов она не видела.
4. Фрагмент приложения (`.boks/_proxy/routes/<app>.json`: хост → `dial <контейнер>:<порт>`, TLS,
   сертификат) и **один reload Caddy для всех портов разом** под серверным замком допуска. Reload
   только если собранный из фрагментов конфиг отличается от применённого (`.boks/_proxy/caddy.json`).
   Прокси запущен с `net.ipv4.tcp_migrate_req=1`: без него reload сбрасывает соединения из очереди
   accept закрывающегося слушателя (93 сброса на 10 reload), с ним — 0. Хосты, которые конфиг больше
   не описывает, уходят тем же reload. Том называется `<app>.<volume>`: точки нет ни в одной половине,
   и склейка однозначна (с дефисом `a-b` + `c` и `a` + `b-c` давали одно имя).
   Файлы из репозитория приложения (`files: [локальный:/путь/в/контейнере]`, G2 2026-10-06) —
   не тома: у каждого релиза своя копия в `.boks/<app>/files/<release>/`, монтируется `-v …:ro` по
   абсолютному пути. Каталог 0700 (другие пользователи хоста не дотянутся), файл 0644 (пользователь
   контейнера любого uid читает — bind-mount проверяет права файла, а не каталогов над ним на хосте;
   проверено на свежем каталоге с nginx от uid 101). Откат монтирует файлы своего релиза; снимок —
   формат 6; Prune удаляет их вместе со снимком.
   Расписания (`schedules: [{name, cron, command}]`, G6 2026-10-06) — cron хоста, не контейнер-
   планировщик (лишний процесс с docker.sock, а метки контейнера не говорят, какая копия обслуживает;
   разбор codex). Строка crontab вызывает `sh .boks/<app>/boks-job <app> <job>` (у каждого приложения своя
   копия, пишется под его блокировкой деплоя; через `sh` — без отдельного chmod); тот читает
   `.boks/<app>/serving` (релиз и его контейнер одной строкой, пишется после записи релиза — после
   отката контейнер новый, а id релиза старый) и запускает команду релиза из
   `.boks/<app>/jobs/<release>/<job>.sh` через `docker exec -i … sh -s` (в crontab команды нет — `%` не
   ломает строку). Пропуск с причиной в `.boks/<app>/jobs/<job>.log`: идёт деплой приложения, в релизе
   нет задания, копия не работает, прошлый запуск не кончился (`flock`). Журнал ограничен: больше 1 МБ —
   уходит в `.log.1` в начале следующего запуска, под замком задания (запуск, сработавший поверх
   идущего, его журнал не трогает); один запуск хранит не больше 1 MiB своего вывода — остаток
   дочитывается через FIFO и считается, задание не получает SIGPIPE, код выхода — его (B5,
   2026-10-06). Блок crontab приложения между
   маркерами `# boks:<app>` заменяется целиком после записи релиза, под `flock .boks/crontab.lock`
   (деплои разных приложений держат разные блокировки, а admission отпущена до записи релиза); без расписаний — один вызов,
   который снимает блок, только если он был. Cron — пять полей, проверенных до изменений (числа в пределах поля, `*`, диапазоны, списки,
   шаги), UTC; приложение с расписаниями — на одном сервере (cron каждого сервера запускал бы
   задание в своей копии); нет cron/flock на сервере —
   отказ до изменений. Снимок — формат 8; Prune удаляет команды релиза.
5. Drain: старый сервер Caddy дорабатывает запросы к прежней копии; boks ждёт, пока у её адресов в
   `/reverse_proxy/upstreams` есть запросы в полёте, но не дольше `drain_timeout` (30 с, как у
   kamal-proxy). Затем остановка и удаление предыдущего контейнера. WebSocket'ы других приложений
   reload не рвёт: у маршрутов `stream_close_delay` 24h (по умолчанию Caddy закрыл бы их сразу).
6. Оставить последние N образов под rollback, старше — `docker image rm`.

Порт может занимать путь хоста (`path`, префикс), срезать его (`strip_path`) или заменить
(`path_rewrite`), менять заголовки запроса и ответа (`headers`, пустое значение удаляет; `X-Forwarded-*`
нельзя — ими владеет прокси) и служить wildcard-хостом (`*.домен`, с TLS только под `cert:`). Порядок
маршрутов в конфиге — правило маршрутизации: точные хосты раньше wildcard, на одном хосте длинный
путь раньше короткого, голый хост последним, неизвестный хост — 404 (C2–C4, 2026-10-06). Хосты сравниваются, как сравнивает Caddy: `idna.ToASCII`, затем нижний регистр
(`internal/hostname`) — `пример.рф` и `xn--e1afmkfd.xn--p1ai` у двух приложений один хост и отказ;
заглавные вне ASCII — отказ конфига (Caddy переводит в punycode до смены регистра, а браузер — после,
и маршрут на `ПРИМЕР.РФ` не совпал бы ни с одним запросом; B1, 2026-10-06).

**Серверная политика** (`server.yml`, C5) — то, что принадлежит серверу, а не приложению: фильтр ботов
по User-Agent. Лежит в инфраструктурном репозитории, применяется `boks server apply` (ревизия
`floor + 1`, под замком допуска, с журналом в `.boks/_server/`), откатывается `boks server rollback`.
Конфиг Caddy собирается из политики и фрагментов приложений: блоки первыми на :80 и :443, `allow`
важнее любого блока; деплой читает применённую политику и меняет только свой фрагмент. Порт 80 — свой
сервер boks рядом с 443 (редиректы Caddy выключены): блоки, HTTP-маршруты, 308 для TLS-хостов, 404.

Фрагмент пишется до reload, `caddy.json` — после: оборванный между ними запуск оставляет
расхождение, и следующий запуск любого приложения перезагружает Caddy с маршрутами оборванного, а не
возвращает их на прежнюю копию. Неудачный reload может пройти без ответа, поэтому маршруты
возвращаются принудительным reload на прежний фрагмент (старая копия в `overlap` жива) — и только потом новая копия удаляется. Не удалось
вернуть — новая копия остаётся, операция в журнале открыта. Приложение, переставшее публиковать
порты, снимает свой фрагмент тем же reload (а при остановленном прокси — только файлы, их Caddy
загрузит при старте) до удаления старой копии; не вышло — старая копия остаётся.

**Режим замены** (`replace`, C5). `overlap` по умолчанию — поток выше: новая копия рядом со старой,
маршруты переключаются после её health check. `stop-first` — для хранилища с одним писателем
(Convex на SQLite): две копии на одном томе могут его испортить. Старые работающие копии
останавливаются до запуска новой, остановка подтверждается состоянием контейнера; не остановилась —
новая не запускается. Маршруты переходят на новую копию только после её health check. Новая не
поднялась — она удаляется (подтверждённо), старые запускаются снова (тоже с проверкой); маршруты к
ним либо не менялись, либо возвращаются reload'ом до того, как старые копии стартуют. Приложение без маршрутов всегда
`stop-first` (`replace: overlap` для него — ошибка конфига), это один и тот же код. Каждая копия несёт свой режим меткой `boks.replace`, и голосуют
копии, которые стоят на сервере, а не запись журнала о том, что сейчас работает: `stop-first` хоть
с одной стороны — значит `stop-first`. У копии без метки (запущенной до неё) решает форма.

**Лимит памяти** (`memory`, E1) — `docker run --memory`, формат `512m`/`1g` (целое число и единица;
голое число, дроби и `MB` отвергаются). Перед запуском — **предварительная проверка, не гарантия от
OOM**: свободно = `MemAvailable` − сколько ещё могут дорасти до своих лимитов остальные контейнеры −
резерв 256 MiB на прокси, dockerd, sshd и ядро. В `overlap` старая копия остаётся со своим ростом; в
`stop-first` её текущее потребление возвращается, а после остановки сервер измеряется заново. Отказ
первой проверки — до любых изменений приложения и до записи в журнал; отказ повторной (после
остановки) запускает старые копии снова и закрывает запись как `failed`. Допуск сериализуется **серверным** замком
(`/tmp/boks.admit.lock`, общий для всех приложений): в `overlap` — до создания контейнера, в
`stop-first` — пока новая копия не поднимется или старая не вернётся. Замок берёт каждый деплой, а
проверку делает только приложение с `memory`: без лимита сравнивать не с чем. Лимит и режим входят
в снимок релиза; откат восстанавливает лимит релиза (и его отсутствие).

**Команда и сигнал остановки** (`command`, `stop_signal`, G4/G8 2026-10-06). `command: [программа,
аргументы…]` — CMD образа в exec-форме, без оболочки; ENTRYPOINT образа по-прежнему получает её
аргументами. Переменную из env подставляет своя оболочка приложения — `[sh, -c, 'exec docker-entrypoint.sh
redis-server --requirepass "$REDIS_PASSWORD"']`, секрет остаётся в env-файле (но после подстановки
виден в argv процесса). Через `docker-entrypoint.sh`, а не `redis-server` напрямую: entrypoint образа
понижает права до пользователя `redis` (gosu), только когда первый аргумент — `redis-server`, а
команда с `sh` в начале его обходит, и Redis работал бы от root (B2, 2026-10-06). Пустой `command:`, `[]`, пустая
программа и null-элемент — ошибка конфига; пустой аргумент пишется `""`. `stop_signal: SIGINT` →
`docker run --stop-signal`. Оба входят в снимок релиза (формат 7); откат запускает записанные, релиз
без них — с CMD и STOPSIGNAL образа.

**Rollback:** `boks rollback app@version` — тот же поток с уже присутствующим образом.
**Multi-port:** N маршрутов на один контейнер в одном фрагменте; переключаются одним reload.
**Lock:** файл-lock на сервере на время деплоя (как `kamal lock`), чтобы два запуска не
переплелись.
**Webhook / push-деплой:** приёмника на сервере нет — GitHub Actions на push запускает
`boks deploy` (SSH-ключ в secrets), как уже делается для Bravo/Shchr. Тонкий приёмник —
только если CI-путь окажется неудобным.

**Preview на PR** (`boks preview up app pr-123` / `down`):
домен `pr-123.<app-domain>` (wildcard-сертификат), база `CREATE DATABASE app_pr123 TEMPLATE app`
(или пустая — **решить**), контейнер, сервис в прокси; `down` из Actions на закрытие PR; GC
preview старше N дней. Уроки Dokploy: всегда свежий образ по SHA (никаких stale-чекаутов),
удаление — по лейблам, чтобы не оставалось сирот.

## Сеть

**Что работает и остаётся.** Контейнеры приложений запускаются без публикации портов на хост
(`runArgs`, `internal/deploy/deploy.go`): наружу на сервере торчит единственный контейнер —
прокси (Caddy) с 80 и 443. Приложение нельзя дёрнуть мимо прокси ни по IP, ни по порту.

**Пробел, подтверждённый автором 2026-09-15.** Сеть одна на весь сервер (`boks` по умолчанию), и
в неё складываются все приложения: изоляции между ними нет, любой контейнер видит любой другой.
Вдобавок у контейнера нет стабильного имени внутри сети — оно уникально на каждый деплой
(`<app>-<tag>-<unix>`), а `--network-alias` не выставляется вовсе. Прокси новое имя узнаёт при
переключении маршрута, сосед по связке — нет. Одиночное приложение этого не замечает (стенд
`boks-lab` — один контейнер Convex), связка из двух контейнеров развалилась бы на втором деплое,
причём молча: старое имя просто перестаёт резолвиться.

**Лечение:**

- сеть на приложение — `boks-<app>` вместо общей;
- `--network-alias <app>` каждому контейнеру: стабильное имя, переживающее деплой;
- прокси подключается в сети тех приложений, чьи маршруты держит (`docker network connect`);
- сеть убирается вместе с приложением, иначе сети копятся так же, как копились бы образы без
  `prune`.

**Сделано (#18, первая часть; 2026-10-04).** Ключ `network` из `boks.yml` убран — конфиг с ним
отвергается с объяснением, а не молча. Контейнер приложения запускается в `boks-<app>` (сеть создаётся
деплоем с меткой `boks.app=<app>`) с `--network-alias <app>`. Прокси живёт в своей сети `boks` и
подключается к `boks-<app>` только у приложения с маршрутами — перед первым переключением маршрута,
не раньше, так что деплой, упавший до маршрутов, прокси никуда не добавляет; приложение, потерявшее
маршруты, отключает прокси от своей сети после проверенного снятия маршрутов. До любых изменений (и
ещё раз под серверным замком допуска) деплой отказывает, если `boks-<app>` существует, но сделана не
для этого приложения, или если имя, которое приносит в сеть новый контейнер (его имя, алиас) либо
прокси (имя, hostname, короткий id), там уже отвечает у контейнера другого владельца; копии самого
приложения — не конфликт. Снимок релиза (формат 3) хранит сети и алиасы, откат возвращает
записанные; снимок до формата 3 возвращается в `boks-<app>` с алиасом (с предупреждением), а не в
общую сеть — алиас принадлежит приложению, не релизу. Мультисерверный откат проверяет сеть на всех
серверах до первого изменения. Удаление сети — вместе с `boks rm` (#22).

**Переход с общей сети.** Старые контейнеры и прокси, поднятый прежним boks, остаются в общей сети
(`boks` или та, что была в `network`, у convex-lab — `boks-test`); её никто не удаляет. Первый деплой
в новой схеме создаёт `boks-<app>`, запускает новую копию там и подключает к сети работающий прокси до
первого переключения маршрута; прокси находит копию по имени через общую с ней сеть, старые
маршруты до переключения идут к старой копии по общей. Возврат при сбое (оживление в `stop-first`,
маршруты на прежний фрагмент) возвращает старую копию в её же сеть — `docker start` сети не меняет —
и маршруты туда, где прокси по-прежнему есть. Замер на boks-lab 2026-10-04 (Docker 29.8): со второй сетью шлюз прокси
по умолчанию переходит на сеть приложения, выход наружу и приём 80/443 при этом работают — после
подключения, после перезапуска прокси и после его пересоздания.
Каждый запуск прокси (`proxy boot`, деплой, сертификат) подключает его к сетям контейнеров, на которые
ведут его маршруты, если он ещё не там: прокси, созданный заново (контейнер удалён, маршруты остались во
фрагментах `.boks/_proxy/`), возвращается и в сети приложений, и в прежнюю общую, а запуск, оборванный между созданием и
подключением, доводит следующий. Сверка строгая: цель, которой уже нет, — предупреждение (её маршрут
чинит деплой приложения), любой другой сбой — отказ запуска, потому что маршрут к работающему, но
недостижимому контейнеру — это авария, а не успех. Сети прокси — общее состояние сервера, поэтому все,
кто их меняет, делают это под серверным замком допуска (`/tmp/boks.admit.lock`, #51): запуск прокси со
сверкой, подключение прокси к сети приложения перед переключением и отключение от сети приложения,
потерявшего маршруты. `boks proxy boot` и `boks cert` берут замок под держателем `_proxy` (не имя
приложения); оставленный ими замок снимает `boks unlock`.

**Связка — несколько приложений с явной связью, не compose** (пересмотрено 2026-10-02, первый
реальный малый сервер; запись 15.09 допускала compose внутри сети приложения). Компоненты связки
живут в разном ритме — у glavdoroga Convex на закреплённой сборке меняется раз в месяцы, Next — на
каждый коммит, Redis — стоковый, — а журнал релизов ведётся на приложение: compose-деплой сцепил бы
их откаты в один. Поэтому `uses: [<app>…]` в `boks.yml` подключает контейнер к сетям названных
приложений, а имя резолвится их алиасом. Контракт, без которого `uses:` не вводится (разбор codex
2026-10-02):

- снимок релиза хранит все сети и алиасы, откат восстанавливает прежние связи, а не сегодняшние;
- деплой отказывает до любых изменений, если зависимость не развёрнута или не здорова;
- `rm` зависимости, у которой есть потребители, — отказ; `rm` потребителя отсоединяет его от чужих
  сетей, не удаляя их;
- одинаковые алиасы разных владельцев в одной сети — отказ;
- прокси подключается только к сетям маршрутизируемых целей, не транзитивно ко всем `uses`.

Известные ограничения: в режиме `overlap` алиас резолвится в обе версии, и потребитель может
попасть в ещё неготовую; `uses:` — сетевое членство, а не ACL: два потребителя одной зависимости
видят друг друга.

**Сделано (#18, вторая часть; 2026-10-04).** `uses: [<app>…]` в `boks.yml` (имена приложений, не
само приложение, без повторов). Контейнер запускается в своей сети с алиасом, затем подключается к
`boks-<dep>` каждой зависимости без алиаса — до старта (`docker create` → `docker network connect` →
`docker start`), чтобы процесс не запустился раньше, чем резолвится зависимость; созданная копия,
которую не удалось подключить или запустить, удаляется. Проверка до любых изменений и ещё раз под
серверным замком допуска: сеть `boks-<dep>` есть и сделана boks для `dep` (иначе `dep` не развёрнут
этим boks — отказ, сеть зависимости деплой не создаёт); у алиаса `dep` в ней есть запущенная копия, и
каждая запущенная копия с этим алиасом `healthy` по health check своего контейнера (`HEALTHCHECK`
образа или блок `healthcheck:` её `boks.yml`) — потребитель ходит к ней по имени мимо прокси, так
что копия без health check получает отказ; алиас `dep` там не отвечает у
контейнера другого владельца; имя нового контейнера там свободно. Имена сравниваются без учёта
регистра, как их сравнивает DNS Docker. Снимок релиза (формат 4) хранит `uses` и сети зависимостей
после своей; откат подключает и проверяет зависимости записанного релиза, а не сегодняшнего конфига,
и отказывает снимку, чьи сети не совпадают с его `uses` по порядку. Прокси подключается только к
своей сети маршрутизируемого приложения — и при деплое, и при сверке сетей на запуске прокси (у цели
маршрута с `uses` прокси идёт только в её `boks-<app>`).

**Требования к `boks rm` (#22), из контракта выше:** `rm` зависимости, у которой есть потребители
(контейнеры других приложений в её сети), — отказ с их перечнем; `rm` потребителя отключает его от
чужих сетей, не удаляя их; сеть `boks-<app>` удаляется вместе с приложением, прокси от неё
отключается под серверным замком допуска.

**Firewall хоста ведёт Docker** (решение автора 2026-10-02). Замер на egress-VDS Selectel: при
`iptables=false` порт прокси публикует userland `docker-proxy`, и приложение видит адрес шлюза
Docker вместо клиента (запрос с 87.228.113.239 пришёл как `X-Forwarded-For: 172.17.0.1`) — все
посетители один адрес, один бан закрывает сайт всем; вдобавок `ip_forward=0`. Сеть boks на таком
сервере непригодна, а своя таблица nft со своими правилами не перекрывает чужой `forward policy
drop` и стирается чужим `flush ruleset`. Поэтому Docker сам управляет правилами (DNAT сохраняет
адрес клиента). Конфиг хоста `boks server install` не переписывает: включённый nftables с `flush
ruleset` — отказ с адресным планом исправления, которое владелец делает сам: вместо `flush ruleset`
— удаление только собственных таблиц конфига хоста (таблицы Docker не трогаются), в его forward
пропускаются мосты boks, `ip_forward` постоянный; проверка — reload и перезагрузка с живыми чужими
процессами (tinyproxy, fail2ban).

**Адрес посетителя за Caddy** (проверено на 2.11.7, 2026-10-06): `trusted_proxies` не задан, и Caddy
заменяет `X-Forwarded-For` адресом соединения, а `X-Forwarded-Proto`/`-Host` ставит от самого запроса —
решение #48 держится без настройки; тест конфига проверяет, что `trusted_proxies` не появился.
`Forwarded` (RFC 7239) Caddy пропускает как есть — каждый маршрут его удаляет, как срезал kamal-proxy.
Пользовательские `header_up` (C3) не должны задавать эти заголовки. Приложению можно верить XFF и
нельзя — `X-Real-IP` и подобным, которые Caddy не трогает. За kamal-proxy то же самое требовало флага
`--forward-headers=false` в каждом `deploy` (без `tls` kamal-proxy по умолчанию сохранял входящие
`X-Forwarded-*`; решение владельца 2026-10-04, #48: доверенного прокси перед boks нет). Если перед
boks появится настоящий upstream (CDN и т.п.), доверие ему — отдельное поле конфига, сейчас его нет.

## Слой данных

**Postgres на всё, один инстанс на сервер, database на приложение.** Не схемы: правило «без
FK между приложениями» делает единственное преимущество схем ненужным, а database даёт то же
(`pg_dump dbname`, `DROP DATABASE`, `GRANT CONNECT`), плюс изоляцию расширений, плюс
совместимость — self-hosted Convex владеет базой целиком; 7 из 8 Convex-приложений уже так и
живут на общем инстансе. Footprint консолидации — операционный: реальная цена инстанса
10–180 MB рабочего набора, дублируются только фоновые процессы (~25 MB на инстанс).

**Redis не запрещён платформой** (решение R3, 2026-10-02,
`docs/plans/20261002-small-box-reality.md`; довод плана о Redis как защите парка снят 2026-10-04,
kopandante/todo#247). Redis — приложение как любое другое (без маршрутов, готовность по
`HEALTHCHECK` образа или `healthcheck:` в `boks.yml` — стоковый образ Redis своего не
объявляет). Общий Redis нескольких серверов — отдельное решение (доступ между
серверами, аутентификация, сохранность, поведение при отказе), `uses:` его не даёт. Ниже —
предпочтение для нового кода, а не ограничение.

**Для нового кода — «всё в Postgres».** Приложения следуют паттерну: очереди —
`pgmq`, расписания — `pg_cron`, кэш — unlogged-таблицы, шифрование — `pgcrypto`. Свой образ
Postgres с этими расширениями — поддерживаемый артефакт boks (`pg_cron` требует
`shared_preload_libraries` и живёт в одной database; образ должен быть multi-arch). Существующие
приложения на Redis пришлось бы переделывать; 1.1 GB feed-кэша на Habsida при этом не исчез бы,
а переехал (сослагательное наклонение здесь намеренно — см. «Область применения»).

**Провижининг** (`boks db create app`): database + роль с `CONNECTION LIMIT`,
`statement_timeout`, `idle_in_transaction_session_timeout`; мониторинг возраста транзакций на
уровне инстанса (xmin horizon общий). Осознанный компромисс: один процесс Postgres — общие WAL/
checkpointer/autovacuum, шумный сосед виден всем; лимиты на роль это смягчают.

**Бэкапы:** `pg_dump` каждой database по расписанию → R2 (S3-совместимое; креды есть, текущее
использование не подтверждено). **Спроектировать.**

## TLS

- Обычные домены: автоматический HTTPS Caddy (ACME HTTP-01), хранилище в томе `boks-proxy-data`;
  редиректы Caddy выключены: http→https (308) для TLS-хостов ставит свой маршрут boks на :80, после
  маршрутов хостов без TLS, затем 404. TLS-хосты — на сервере :443 с HTTP/1.1 и HTTP/2
  (443/udp не опубликован, HTTP/3 выключен), хосты без `tls` — на :80.
- Wildcard (нужен уже сейчас — Shchr, preview): `lego` DNS-01 → сертификат на сервер в том
  `boks-certs` прокси (файлы от root, 0640: Caddy работает от root) → `load_files` в конфиге, хост
  исключён из ACME (`skip_certificates`). Конфиг с отсутствующим файлом Caddy отвергает (старый
  работает дальше), а стартующий с таким конфигом Caddy падает — поэтому деплой проверяет файл до
  запуска копии.
- **Ротация (проверено 2026-10-06):** Caddy читает файлы, когда загружает конфиг; reload
  неизменного конфига их не перечитывает, `caddy reload --force` и изменённый конфиг — перечитывают.
  `boks cert renew` ставит файлы и делает `reload --force` под замком допуска; любая загрузка
  покрывает все маршруты сервера, поэтому отметка о загрузке одна (не на приложение). Каталоги-поколения
  сертификатов (#19) не сделаны.
- **Где хранится состояние lego — открытый вопрос, и он мешает автоматическому продлению.**
  Каталог `.lego` содержит приватный ключ сертификата и ключ ACME-аккаунта. На машине оператора
  это нормально (он в `.gitignore`), а вот перенос продления в CI упирается в то, что хранить
  этот каталог негде: кэш GitHub Actions не хранилище секретов — кэш, записанный прогоном на
  основной ветке, восстанавливается прогонами из любой ветки того же репозитория, включая
  pull request. Поэтому примера workflow здесь намеренно нет. Два честных пути: продлевать там
  же, где живёт `.lego` (таймер на машине оператора), либо держать ключ аккаунта в настоящем
  хранилище секретов, а текущий сертификат забирать с сервера перед запуском lego — для второго
  в boks пока нет команды выгрузки, это отдельная работа.
- **Где живёт выпуск:** на стороне оператора/CI, не на сервере — DNS-токены нередко
  ограничены по IP (так у токена Cloudflare для `kopanda.ru`: с сервера ошибка 9109, с ноутбука
  работает). Это совпадает с тем, что boks и так живёт на ноутбуке/CI. Cron продления — в
  Actions или на ноутбуке, с алертом в Telegram при неудаче: урок Traefik, где автопродление
  молча не работало месяцами. Решение 2026-09-15 — перенести продление на сам сервер таймером
  (#28, `docs/plans/20260915-decisions.md`, E4); блокер — DNS-токен, который принимают с этого
  сервера, и до него действует описанное здесь.

## Логи и метрики

Ядра нет — хранить нечего. Логи: json-file контейнеров → Alloy → Loki (обязательный элемент платформы,
может бежать на другом инстансе). Метрики: существующий Prometheus-стек (node-exporter,
cadvisor уже стоят) — boks ничего не рисует и не хранит.

## Секреты

Источник правды — bws. `boks deploy` берёт env приложения из bws → env-file на сервере (0600)
→ `--env-file` контейнеру. Никогда не печатаются; `boks env` показывает маски. API у boks решено
завести (2026-09-15, кода ещё нет), и правило для него записано явно — см. «Control API, UI и агент»: наружу идут имена и
маски, значения не отдаются ни на чтение, ни эхом на запись. Ровно то, чего не делает API
Dokploy, отдающий переменные окружения и пароли от registry целиком в теле ответа на мутации.

**SSH-соединения.** Вызовы одного запуска идут через одно соединение на сервер (`ControlMaster`,
сокеты в `/tmp/boks-*` этого запуска, закрываются в конце; `BOKS_SSH_MUX=0` выключает): до дальнего
сервера новое соединение стоит секунды, а в stop-first они приходились на простой приложения.

## Состояние и конфигурация

Центрального состояния нет. Правда на каждом сервере — это Docker (лейблы контейнеров), журнал
релизов в `.boks/<app>/`, фрагменты маршрутов прокси в `.boks/_proxy/` (Caddy загружает собранный из
них конфиг при старте) и серверная политика в `.boks/_server/`; `boks ps` и `boks proxy list` читают
релизы и фрагменты, `boks server status` — политику. На
стороне оператора — `boks.yml` в репозитории приложения (серверы, образ, хосты→порты, health
check, база) и SSH-алиасы серверов. Серверы независимы; `boks ps --all` опрашивает их
параллельно, недоступный сервер показывается как недоступный, не блокируя остальные.

## Control API, UI и агент

Решение автора, 2026-09-15: **на каждом сервере локально работает защищённый API, к которому
подключаются UI и LLM.** Оно отменяет три прежние записи — «на серверах нет control API», «у boks
просто нет API, который мог бы отдать секреты» и «никакого UI в v1». Что встаёт на их место:

**Форма.** Отдельный процесс на сервере (`boksd`), слушает свой порт и сам терминирует TLS. Через
прокси он намеренно не идёт: control-plane не должен зависеть от data-plane — когда прокси
лёг, API нужен именно для того, чтобы это увидеть и починить. Команды выполняет локально, тем же
кодом, каким CLI выполняет их по SSH. *Вывод мой из решения автора, не его слово.*

**Кто пускается — взаимный TLS.** Сервер проверяет клиентский сертификат, клиент проверяет
серверный. Подбирать нечего, в истории команд и логах прокси ничего не оседает (в отличие от
bearer-токена, который был выбран в v1), отзыв — списком на сервере. Нужна своя маленькая CA:
корень на сервере, клиентские сертификаты выдаются поимённо — оператору, UI, агенту, — чтобы в
журнале операций было видно не «кто-то с токеном», а кто именно. Как это совмещается со входом
человека по passkey, которому импортировать сертификат не нужно, — `docs/plans/20260915-decisions.md`, A2.

**Что умеет — всё, что умеет CLI.** Чтение: состояние контейнеров, маршруты прокси, логи,
сертификаты, версии. Операции: деплой, откат, рестарт, переменные. Отсюда обязательный журнал:
кто (из сертификата), что, когда, чем кончилось.

**Секреты наружу не отдаются.** Ни в ответе на чтение, ни эхом на запись — только имена и маски.
Это прямой урок Dokploy, чей API отдаёт переменные окружения и пароли от registry целиком в теле
ответа на мутации.

**LLM — через тот же CLI, MCP не строим** (решение автора 2026-09-15). Агент сидит на машине
оператора и умеет запускать команды: `boks ps` через shell даёт ему ровно то, что дал бы
MCP-инструмент, без второго интерфейса, который надо держать в синхроне с CLI. Взамен у CLI
появляется то, чего ему правда не хватает, — **машинный вывод `--json` у каждой команды**; сейчас
все команды печатают текст для человека. MCP вернётся, только если появится агент без шелла:
веб-агент или чужая песочница, где есть HTTP и клиентский сертификат, но нет ни SSH, ни бинарника.

**UI — тонкий клиент.** Держит список серверов с адресами и сертификатами, ходит к каждому
параллельно, сводный обзор собирает у себя; межсерверной координации нет, один недоступный сервер
не должен ронять отображение остальных — у каждого подключения своё состояние и свой индикатор.
Где он запущен — вопрос удобства, а не архитектуры: обычно на машине оператора, но **при желании
его можно поднять и на одном из серверов** как обычное приложение boks, и тогда он доступен
из любого браузера.

**Паролей нет нигде — это требование автора (2026-09-15), а не побочный эффект.** Сегодня их и
так не набирают руками: SSH — ключи, control API — сертификаты, пароли ролей Postgres и токены
registry машинные, живут в bws. Единственное место, где пароль мог бы завестись, — вход человека
в браузерный UI. Поэтому `boksd` принимает **два удостоверения**:

| Кто | Чем удостоверяется |
|---|---|
| CLI, агент, автоматика | клиентский сертификат (mTLS) |
| человек в браузере | passkey/WebAuthn — Touch ID или аппаратный ключ |

Так снимается и цена браузерного UI: импортировать клиентский сертификат в каждый браузер не
нужно, подбирать нечего, фишинг не работает, а UI остаётся статикой и может лежать где угодно —
на машине оператора или на одном из серверов как обычное приложение boks. Журнал видит именно
человека: UI ничего не подписывает от своего имени и посредником не становится.
*Разбор мой из требования автора.*

**CLI ходит через тот же control API** (решение автора 2026-09-15, отменяет мою прежнюю запись
«CLI остаётся SSH-путём»). Вход на сервер один: и человек в браузере, и агент, и CLI приходят в
`boksd`, различаясь только удостоверением. Отсюда сразу два упрощения — журнал операций видит
всё, что происходит с сервером, без исключений, и замок деплоя один по построению, а не по
договорённости между двумя путями.

SSH остаётся ровно для того, без чего API не существует: установки boksd на чистый сервер, его
обновления и снятия. Это не второй способ управления, а начальная загрузка.

**Футпринт.** Постоянный процесс на сервере теперь есть — бюджет единицы мегабайт RSS против
780–900 MB Node у Dokploy. Замерить на стенде до раскатки.

**Открыто:**
- откуда API берёт секреты приложения при деплое: сейчас их подставляет оператор из bws, а деплой
  через API идёт без оператора;
- выпуск, раздача и ротация клиентских сертификатов — руками или командой boks;
- что делает API, когда просят операцию, которой нужен DNS-ключ (выпуск сертификата): на сервере
  этого ключа может не быть вовсе;
- регистрация первого passkey: с чего начинается доверие на чистом сервере (кандидат — команда по
  SSH, то есть тем ключом, который уже есть);
- потеря устройства с passkey: резервный путь должен быть, и он не может быть паролем — кандидат
  тот же SSH-доступ плюс отзыв старого ключа.

## Установка сервера

`boks server install <server.yml>` готовит пустой или уже совместимый сервер. Ему хватает файла с
одними `servers:`: политику он не применяет, это делает `server apply`, поэтому ревизия не нужна.
Каждый сервер сначала прочитан одним скриптом, без изменений. Отказ приходит до любой правки, с
причиной и с тем, что сделать. Отказывает, если:

- ОС не Debian 12+ или Ubuntu 22.04+ с systemd;
- нет ни root, ни `sudo -n`;
- ядро без `tcp_migrate_req`;
- `boks-proxy` — kamal-proxy прежнего boks (его переносит `boks proxy migrate`);
- порт 80 или 443 занят не прокси boks (назван процесс или контейнер);
- Docker работает в Swarm или rootless;
- Docker старее API 1.44, или у пакета `docker.io` кандидат старше 25;
- `daemon.json` или флаг dockerd задаёт `iptables: false` или `bridge: none`;
- nftables включён с `flush ruleset`.

На Debian 12 пакет `docker.io` — 20.10, поэтому там Docker Engine ставится заранее из репозитория
Docker (docs.docker.com/engine/install), и уже потом `boks server install`; с пустого сервера одной
командой — Ubuntu 22.04+ и Debian 13+. Чужую инфраструктуру boks не мигрирует.

Затем, под замком допуска и с записью в `.boks/_server/journal.jsonl`, факты перечитываются и
выполняются шаги:

- **Пакеты.** Ставятся только недостающие из `docker.io`, `cron`, `util-linux`, без общего upgrade;
  на Debian 13 ещё `docker-cli` — там клиент отделён от `docker.io` и тот его только рекомендует.
  apt ждёт чужой замок до 5 минут: на свежей машине его держит unattended-upgrades.
  Индекс пакетов обновляется ещё в предпроверке, до изменений на любом из серверов, и только когда
  ставить есть что: на свежем образе индекса может не быть или он старый, и версия `docker.io`
  проверяется по свежему. Ждётся и замок списков пакетов, который берёт `apt-get update`.
- **`daemon.json`.** Пишется до установки Docker, чтобы dockerd стартовал уже с ним. Существующий
  файл не затирается, а дополняется, чужие ключи сохраняются; где Docker уже стоит, файл
  проверяется `dockerd --validate`; заменяется атомарно, прежний остаётся как `.boks-bak`.
  Добавляются два ключа:
  - ротация логов json-file 3 × 10 MB — для контейнеров, которые запустил не boks; у своих она
    задана явно;
  - пул адресов `10.240.0.0/16` по /24 — только если у Docker ещё нет своих сетей и маршруты хоста
    не пересекают пул.
- **Чего boks не делает:**
  - не пишет в `daemon.json` ключ, который dockerd уже получает флагом (смотрится командная строка
    работающего dockerd, так что флаг из drop-in или файла окружения тоже считается): с опцией,
    заданной дважды, dockerd не стартует;
  - не перезапускает dockerd под работающими контейнерами — вместо этого печатает заметку.
- **Пользователь.** SSH-пользователь, если это не root, добавляется в группу docker. Доступ
  проверяется новым соединением: группа действует только в новом входе.
- **Прокси.** В конце запускается `proxy boot`.

Повторный запуск ничего не меняет и не пишет даже журнал. Отсюда не проверить firewall провайдера
перед 80/443 и поведение после перезагрузки — команда так и говорит.

Проверено на чистой Ubuntu 24.04 (OrbStack) под root и под sudo-пользователем: 30 с до работающего
прокси, повтор — «nothing to change». На сервере с приложениями boks команда только печатает
заметки, dockerd не перезапускается. На узле Swarm — отказ, ничего не записано.

## Исходящий прокси

На сервере один прокси — `boks-proxy`. Он же работает прямым HTTP-прокси для исходящих запросов
сервисов, которым нужен адрес этого сервера: так пул encar ходил через tinyproxy на VDS. Плагин
`forwardproxy` есть только в собственном образе boks: `ghcr.io/kopandante/boks-caddy`, Caddy 2.11.7
и плагин `forwardproxy`, закреплён по digest; Dockerfile лежит в `proxy/`, образ собирает GitHub
Actions. Без `egress:` плагин ничего не делает.

```yaml
# server.yml
servers: [egress1]
revision: 4
egress:
  allow: [203.0.113.10, 198.51.100.0/24]  # кто может ходить; обязателен, /0 запрещён
  user: encar                             # вход, по желанию — вместе с password_env
  password_env: ENCAR_EGRESS_PROXY_PASSWORD
  ports: [443, 80]                        # куда можно, по умолчанию [443]
  hosts_file: /etc/hosts                  # имена через hosts-файл хоста, по желанию
```

Применяется командой `boks server apply`, как остальная политика сервера, с ревизией и откатом.

- **Конфиг Caddy.** Отдельный HTTP-сервер на `port` (по умолчанию 3128). Разрешённый клиент
  (`remote_ip`) попадает в `forward_proxy`, остальные получают 403. Наружу не уходят ни адрес клиента,
  ни имя прокси (`hide_ip`, `hide_via`). Журнала запросов нет. Приватные и loopback-адреса плагин
  не пускает. Адрес клиента Caddy видит настоящий: Docker пробрасывает порт через DNAT.
- **Пароль.** Ни в `policy.json`, ни в истории его нет. Он лежит в `.boks/_server/egress.secret`
  (права 0600) и попадает в `caddy.json` с теми же правами. Новый пароль ставится повтором
  `apply` той же ревизии; каждый `apply` файла с egress требует переменную `password_env`. Откат
  берёт пароль с сервера, если пользователь тот же, а ревизию с другим пользователем отказывает.
- **Контейнер.** Порт egress и hosts-файл задаются только при создании контейнера. Поэтому
  `apply` и `rollback` сначала, на всех серверах файла и до любых изменений, проверяют, что в
  работающем образе есть плагин, что hosts-файл на месте и что пароль для пользователя есть; перед
  подменой Caddy ещё проверяет новый конфиг. Затем прокси пересоздаётся тем же образом (80 и 443 недоступны около секунды), и
  только после этого пишется политика. Если подмена не удалась, старый прокси возвращается. `proxy
  boot` и `proxy upgrade` создают прокси с портом и hosts-файлом из политики.
- **hosts-файл** монтируется по inode. Тот, кто его ведёт, пишет на месте, а не заменой файла: иначе
  прокси останется со старой копией: `boks server status` это покажет, лечит `docker restart
  boks-proxy`. Go перечитывает файл, когда меняются mtime или размер, не чаще раза в 5 с.
- **Сеть.** Порт, опубликованный Docker, обходит input-цепочку хоста, поэтому nft-фильтр перед портом
  не действует. Защита — `allow` и вход, оба на уровне HTTP.
- **Отличия от tinyproxy.** Нет лимита клиентов и простоя соединения. Если цель недоступна, прокси
  отвечает 403, а не 500. На подключение к цели даётся 30 с.

Проверено 2026-10-07 на Debian 13 (OrbStack):
- с входом: 200 на HTTPS и HTTP;
- без входа или с неверным паролем: 407;
- запрещённый порт и приватная цель: 403;
- клиент вне `allow`: 403;
- открытый туннель пережил повторный `apply`;
- запись в hosts-файл на месте видна без перезапуска;
- после перезагрузки машины прокси отвечает.

Переключение пула encar описано в `docs/plans/20261007-egress.md`.

## Безопасность

Сегодня CLI ходит по SSH. По решению 2026-09-15 он переходит на control API (#26), и SSH
остаётся только для установки, обновления и снятия `boksd`; в API машины входят по взаимному TLS,
человек — по passkey. Вместе с демоном появится публичная поверхность — чем она защищена и почему
не bearer-токеном, сказано в «Control API, UI и агент». Приёмника вебхуков по-прежнему нет → нет и HMAC; появится приёмник — появится проверка
подписи.

## Обновления

boks — бинарник на ноутбуке, обновление тривиально. Прокси — `boks proxy upgrade` (G3, 2026-10-06):
`proxy boot` работающий прокси не трогает, а только говорит, что конфиг называет другой образ.
Upgrade под замком допуска и в журнале сервера; до остановки — проверка, что ни одно приложение не
деплоится, pull и `caddy validate` текущего конфига новым образом (Caddy 2.6 отвергнут так, прокси
не тронут); затем старый контейнер отходит в `boks-proxy.old`, новый создаётся, подключается к сетям
маршрутов, стартует и проверяется (admin API, sysctl); не вышло — новый удаляется, старый
возвращается (по контейнерам на сервере: ответ docker по SSH мог потеряться) и должен ответить. Маршруты в `.boks/_proxy/`, сертификаты в томах переживают подмену. **Окно
недоступности — 1–2 с** (boks-lab2, зонд каждые 20 мс, общие SSH-соединения; без них 2–4 с): вызовы
между stop и start идут с ноутбука по одному. У kamal-proxy при `docker restart` было 0,19 с.

## Что такое boks

Формулировка автора, 2026-09-08:

> Это более лёгкий и менее функциональный аналог Dokploy.

Здесь важны оба прилагательных, и второе — не признание недоделанности, а решение. Паритет с
**каталогом функций** Dokploy не является целью: обнаруженная у него функция сама по себе не
довод за то, чтобы она появилась в boks.

**Уточнение автора, 2026-09-15: «нам нужны бесшовные деплои и все удобства».** Это ориентир, а не
программа работ: миграция парка не планируется. Мерка при этом названа — не каталог функций
Dokploy, а то, что реально используется; не поддержанное фактом использования не строим вовсе
(аудит 2026-09-04: MySQL/Mongo, Swarm-кластеризация, marketplace, RBAC, Nixpacks, собственный CLI
Dokploy). С чем сравнивать — срез парка ниже.

Так же читается и аудит Dokploy в этом документе: он описывает, с чем сравнивают, а не список
к реализации. Ровно поэтому из проекта уже выпали Nixpacks (LLM пишет Dockerfile), Traefik
(взяли kamal-proxy), docker compose и веб-интерфейс как обязательная часть ядра.

### Правило Парето

Формулировка автора, 2026-09-08: **покрываем 80% случаев, остальное выкидываем на свалку.**
Пример оттуда же: только GitHub и только Dockerfile.

Это процедура, а не настроение. На каждой развилке берётся доминирующий вариант, а остальные
**не поддерживаются вовсе** — и это не то же самое, что «поддерживаем все, по умолчанию один».
Разница в цене: вариант «по умолчанию» всё равно требует абстракции над всеми вариантами, тестов
на каждый и совместимости при изменениях. Выброшенный вариант не стоит ничего.

Решённые оси:

| Ось | Берём | Выброшено |
|---|---|---|
| VCS | GitHub | GitLab, Bitbucket, Gitea |
| Источник сборки | Dockerfile | Nixpacks и прочий автодетект, docker compose |

Про Dockerfile стоит уточнить, где он вообще живёт: boks ничего не собирает — образ приходит
готовым из реестра. То есть Dockerfile — требование к репозиторию приложения и его CI, а не код в
boks. Ось закрыта тем, что boks не будет уметь ни одного другого источника.

**Граница правила.** Оно про то, что boks строит и поддерживает сам, а не про общность, которую
зависимость даёт бесплатно. Пример из живого кода: `cert.dns` — это имя DNS-провайдера, которое
boks передаёт строкой в lego. Провайдеров у lego под сотню, boks не знает про них ничего и не
тестирует ни одного; сузить поле до `cloudflare` не сэкономило бы ни строки, а отняло бы у
пользователя работающий случай. Такую общность правило не трогает. Трогает оно ту, за которую
платят абстракцией: развилка, требующая интерфейса, ветвления или второго пути в коде.

Чего эта формулировка **не** говорит: кто и где boks запускает. Ни про боевые серверы автора, ни
про других пользователей здесь ничего не сказано, и выводить это отсюда нельзя.

Прежняя редакция этого документа содержала раздел «Миграция с Dokploy» с порядком перевода
серверов (OCI → Shchr → Bravo → Tokyo → Habsida). **Это было моё допущение, а не решение
автора** — удалено 2026-09-05. Данное уточнение области его не возвращает: у замеров, аудита
Dokploy и требований (DNS-01, multi-port, деплой готовых образов) остаётся своя ценность как у
описания реальной среды, но «когда и что переезжает» из них по-прежнему не следует.

## Срез парка 2026-09-15 — справка, не план миграции

Снято по просьбе автора как теоретическое сравнение: переносить существующие серверы **никто не
собирается**, и сроков у этого нет. Таблица отвечает на один вопрос — если однажды снимать
Dokploy, с чем придётся иметь дело.

Живой срез (`docker ps` по серверам): Habsida — 84 контейнера, Tokyo — 20, Bravo — 17,
Shchr — 12. Docker на всех четырёх в режиме Swarm: это рантайм Dokploy, и уход с него означает,
что рестарт-политики, реплики и Swarm-secrets должен обеспечить кто-то другой.

| Что | Факт на серверах | Состояние в boks |
|---|---|---|
| Базы и кэши | 5 postgres + 7 redis на Habsida, по паре на Tokyo (auctions, telegram-bots), свои у riman, kids, shchr, encar | провижининг описан, кода нет |
| Связки из нескольких контейнеров | стек телеметрии на Habsida (prometheus, loki, grafana, alloy, swarm-exporter), Convex + dashboard на Bravo, courier на Tokyo — всё это compose | compose **выброшен решением**; либо разбирать на отдельные приложения, либо пересматривать решение |
| Свой registry | 20 образов на Habsida тянутся с `:5000`, на Bravo стоит `registry:2`, riman — с `registry.cars.habsidev.com` | вход в приватный реестр по HTTPS сделан (E2, блок `registry`, см. «Модель деплоя»); запуск своего реестра и его TLS не продуманы |
| Превью по PR | `dkauto-preview`, `dbauto-preview`, `hanexport:pr-151`, `autohubkorea-convex-preview`, `translationspreview` | замысел |
| Авторизация перед приложением | logto + oauth2-proxy на Shchr | не описано; Caddy умеет `forward_auth` штатно — в boks не выведено |
| Расписания | Dokploy Schedules, cron-пробы, recycler | сделано (G6, `schedules:` — cron хоста + boks-job, снимок v8, приложение на одном сервере); cron-пробы и recycler — не покрыты |
| Метрики | Prometheus, cadvisor, node-exporter уже стоят | эндпоинта `/metrics` нет |
| Логи приложений | смотрят в UI Dokploy | команды `boks logs` нет |
| Фронты, боты, статика, 15 Convex-бэкендов | основная масса | **покрыто** |

**Два препятствия вне этой таблицы.** На Office SSH не ведёт вовсе: 22-й порт занят чужим
HTTP-сервисом, всё управление идёт через API Dokploy — а boks без SSH не умеет ничего, включая
собственную установку. Oracle с нашей сети не отвечает ни по какому порту.

   `kamal-proxy deploy` по каждому порту, стоп старого, lock, откат маршрутов при провале
   переключения. Плюс жизненный цикл сертификатов: `cert issue|renew|status|pull`, доставка в том
   прокси, перезагрузка рестартом, ежедневное продление из GitHub Actions. Без preview, без
   db-провижининга. Работает на `boks-lab`.
3. Control API: `boksd` на сервере, mTLS со своей CA, журнал операций, тонкий клиент UI,
   `--json` у команд CLI. Решение записано 2026-09-15, не реализовано.
4. Дальше — отбор работы по мерке из «Что такое boks»: не «есть в Dokploy», а «реально используется».

## Открыто

- ~~Preview-база: TEMPLATE от prod или пустая~~ — развилку закрывает правило Парето: **только
  `CREATE DATABASE … TEMPLATE <prod>`**, пустая база не поддерживается. Причина: preview с пустой
  базой обычно нечего показывать, а поддержка обоих режимов — это флаг, ветвление и два пути,
  которые надо тестировать. Цена решения: копия базы на каждый PR (для больших баз развилка
  вернётся) и боевые данные в preview-окружении. *Вывод мой из правила автора, не его слово —
  отменяется одним словом.*
- Бэкапы: схема pg_dump → R2.
- `dockerd` 457 MB на Bravo при 16 контейнерах — похоже на утечку, проверить отдельно.
- ~~Продление wildcard-сертификатов~~ — **закрыто 2026-09-08.** Ежедневный workflow в GitHub
  Actions: `boks cert pull` забирает с сервера сертификат и метаданные lego (замерено: именно эти
  два файла lego 5 читает, решая «пора или нет»; приватный ключ в решении не участвует), дальше
  `boks cert renew` — lego молчит, пока не пора. Кэша с состоянием нет, ключ сертификата не
  покидает сервер. DNS-токен без IP-ограничения не понадобился.

# План редизайна конфигурации boks

## Что за проект

boks — тонкий CLI на Go (~2300 строк), замена Dokploy на своих серверах. Живёт на ноутбуке и в
CI, по SSH управляет Docker и kamal-proxy на app-серверах. Образы приходят готовыми из registry,
boks ничего не собирает. Причина существования измерена: control-plane Dokploy — Node-процесс на
780–900 MB на каждом сервере.

Принцип автора: «покрываем 80% случаев, остальное выкидываем на свалку» — на каждой развилке
берём доминирующий вариант, остальные НЕ поддерживаются вовсе (это дешевле, чем «поддерживаем
всё, по умолчанию одно»: у варианта-по-умолчанию всё равно есть абстракция, тесты и
совместимость, а у выброшенного нет ничего).

Новые решения, принятые сегодня (ещё не реализованы, но конфигурация обязана их учитывать):
- на каждом сервере работает control API (`boksd`), к нему подключаются UI и LLM-агент;
- вход: mTLS для машин, passkey/WebAuthn для человека; паролей нет нигде;
- продление wildcard-сертификатов переезжает с GitHub Actions на сам сервер (таймер);
- у каждого сервера СВОЙ wildcard-домен.

## Текущая конфигурация (что переделываем)

Один файл `boks.yml` на приложение, 15 полей верхнего уровня:

```yaml
app: convex-lab
image: ghcr.io/get-convex/convex-backend
servers: [boks-lab]
network: boks-test
proxy_image: basecamp/kamal-proxy:v0.10.0
env_file: .env
env: {DISABLE_BEACON: "true", CONVEX_CLOUD_ORIGIN: "https://..."}
volumes: [data:/convex/data]
ports:
  - {name: api, port: 3210, host: api.lab.kopanda.ru, health_path: /version}
  - {name: actions, port: 3211, host: actions.lab.kopanda.ru, health_path: /version, health_port: 3210}
tls: true
keep: 2
deploy_timeout: 60s
cert: {domains: ["*.lab.kopanda.ru"], dns: cloudflare, email: ..., path: .lego, staging: true, renew_days: 0}
```

## Диагноз: в одном файле смешаны три владельца факта

| Поля | Кому факт на самом деле принадлежит |
|---|---|
| app, image, ports, volumes, env, env_file | приложению (его репозиторию) |
| servers, network, proxy_image, keep, deploy_timeout, tls | серверу |
| cert.* | серверу — у каждого сервера свой wildcard |

Главная ошибка — **cert в конфиге приложения**. Сертификат принадлежит серверу, а записан у
приложения. Отсюда в коде выросло следующее (всё это существует ТОЛЬКО из-за неверного владельца):

1. `internal/cert/cert.go` — 371 строка, из них примерно половина обслуживает последствия:
   - `Pull` — выкачивание сертификата и метаданных lego обратно с сервера, потому что продление
     идёт в чужом CI без приватного ключа;
   - ДВА вида отметок о загрузке: `<slug>.restarted` (прокси перезапускался, читает для всех
     сервисов) и `<slug>.<app>.loaded` (маршруты этого приложения). Разделены потому, что деплой
     одного приложения не должен «расписываться» за другое приложение под тем же wildcard. В коде
     это объяснено комментарием на 15 строк;
   - проверка `tls.X509KeyPair`, что .crt и .key — пара: после `Pull` они могут разъехаться;
   - `ReloadPending` vs `Pending` — два разных вопроса «кто уже перечитал файл».
2. `internal/deploy/deploy.go` — `covered(cfg)`, ранний отказ «run `boks cert issue` before
   deploying an app with a cert block», вызов `cert.MarkLoaded` после переключения маршрутов.
3. Дублирование в конфигах: N приложений под одним wildcard = N копий блока cert (те же домены,
   тот же email, тот же провайдер). Разъедутся — узнаем случайно.

Вторая ошибка — **`servers:` списком в конфиге приложения**. У каждого сервера свой wildcard,
значит `ports[].host` (конкретный домен) и список из нескольких серверов противоречат друг другу:
на втором сервере тот же host невыразим. Реально поддерживается только список из одного элемента.

Третья — **env_file/env**. Архитектура говорит, что источник правды для секретов — bws, а конфиг
предлагает локальный .env-файл рядом с репозиторием. Плюс новое решение «API отдаёт имена и
маски, никогда значения» требует, чтобы имена секретов были известны декларативно.

## Элегантное решение: конфигурация принадлежит владельцу факта

Три файла вместо одного, каждый у своего владельца:

| Файл | Владелец | Что описывает |
|---|---|---|
| `boks.yml` в репозитории приложения | приложение | образ, порты↔домены, тома, имена секретов |
| `/etc/boks/server.yml` | сервер (`boksd`) | сеть, образ прокси, СВОЙ wildcard и DNS, политики хранения, CA |
| `~/.config/boks/contexts.yml` | оператор | к каким серверам хожу, по каким адресам, каким клиентским сертификатом |

### 1. Конфиг приложения — восемь полей вместо пятнадцати

```yaml
app: convex-lab
image: ghcr.io/get-convex/convex-backend
ports:
  - {name: api, port: 3210, host: api.lab.kopanda.ru, health_path: /version}
  - {name: actions, port: 3211, host: actions.lab.kopanda.ru, health_path: /version, health_port: 3210}
volumes: [data:/convex/data]
env: [INSTANCE_NAME, INSTANCE_SECRET]      # ИМЕНА секретов, значения берутся из bws
vars: {DISABLE_BEACON: "true", CONVEX_CLOUD_ORIGIN: "https://api.lab.kopanda.ru"}
```

Убрано и почему:
- `cert` → на сервер. Сервер знает свой wildcard и сам подставляет пути к файлам для тех хостов,
  которые этот сертификат покрывает. Приложение про сертификаты не знает ничего.
- `servers` → в контексты оператора; приложение живёт на одном сервере (правило Парето),
  сервер указывается `boks -s <имя>` или дефолтным контекстом.
- `network`, `proxy_image`, `keep`, `deploy_timeout` → на сервер: это его сеть, его диск, его
  политика.
- `tls` → выкинуто: app-сервер публичный, TLS всегда.
- `env_file` → выкинуто; `env` меняет смысл с «значения» на «имена секретов в bws», открытые
  значения переезжают в `vars`, чтобы секрет и не-секрет нельзя было перепутать глазами.

### 2. Конфиг сервера

```yaml
network: boks
proxy_image: basecamp/kamal-proxy:v0.10.0
keep: 3
deploy_timeout: 60s
cert:
  domains: ["*.lab.kopanda.ru"]
  dns: cloudflare
  email: kan.evgenii.dev@gmail.com
  renew_days: 30
api:
  listen: ":8443"
  ca: /etc/boks/ca.crt
```

### 3. Контексты оператора

```yaml
default: boks-lab
servers:
  boks-lab: {ssh: boks-lab, api: https://boks-lab.kopanda.ru:8443, cert: ~/.config/boks/boks-lab.p12}
```

## Что из кода исчезает вслед за этим

- `cert.Pull` целиком и команда `boks cert pull` — продление идёт на сервере, где лежит ключ.
- Проверка пары crt/key — разъехаться нечему, оба рождаются на месте.
- Отметка `<slug>.<app>.loaded` и разделение `Pending`/`ReloadPending` — владелец сертификата
  один (сервер), перезагрузка прокси после продления общая, и сервер знает, когда её сделал.
- `covered()`, `MarkLoaded` и ранний отказ в `deploy.go` — приложение больше не отвечает за
  сертификат; путь подставляет сервер, а если файла нет, отказывает он же и одинаково для всех.
- `EnvContent` — чтение локального .env-файла заменяется на выдачу значений из bws по именам.

Ожидаемое сжатие `internal/cert`: с 371 строки примерно до 150 (выпуск через lego, установка,
перезагрузка прокси, чтение срока).

## Требования, которые решение обязано выполнить

1. Деплой без простоя: pull → run → переключение прокси по каждому порту → гашение старого.
2. Откат на предыдущую версию; при срыве переключения — возврат маршрутов на старый контейнер,
   с портами ТОГО контейнера (сейчас читаются из лейбла `boks.ports`).
3. Wildcard-сертификат: выпуск, установка, перезагрузка прокси (kamal-proxy держит сертификат в
   памяти и файл не перечитывает), автопродление.
4. Обычные домены — autocert самого kamal-proxy; одно приложение может смешивать оба вида.
5. Секреты: значения не печатаются, наружу только имена и маски.
6. Несколько приложений на одном сервере под одним wildcard не мешают друг другу.
7. Конфигурация должна быть готова принять `boksd` (control API, mTLS, passkey) без ломки формы.

## Ограничения

- Go, без демона на сервере СЕГОДНЯ (демон появится, но CLI обязан работать и по SSH).
- Правило Парето: одно приложение — один сервер; только GitHub; только Dockerfile.
- Не ломать работающий стенд `boks-lab` (Convex на двух портах под двумя доменами).

## Критерии, по которым судить дизайн

- меньше абстракций и меньше кода, чем сейчас, при тех же требованиях;
- каждый факт записан ровно в одном месте и у своего владельца;
- невозможные состояния невыразимы (нельзя описать сертификат, противоречащий серверному).

# Разбор внешней критики (codex, 2026-09-15) и итоговая форма

Приняты все восемь замечаний; два — в суженном виде. Критика поймала главное: в запале
«элегантности» я выбросил два защитных механизма и добавил одну преждевременную абстракцию.

| # | Замечание | Решение |
|---|---|---|
| 1 HIGH | смена владельца не устраняет состояние «файлы установлены, прокси не перезапущен» | **принято.** Один серверный отпечаток загруженного сертификата остаётся. Уходит только отметка на приложение и раздвоение `Pending`/`ReloadPending` |
| 2 HIGH | перенос выпуска на сервер упирается в DNS-токен, отклоняемый с серверов (9109) | **принято.** Доступ сервера к DNS API — явное условие миграции; рабочий путь выпуска не удаляется, пока условие не проверено |
| 3 MED | `contexts.yml` вводит реестр подключений и транспорт раньше `boksd` | **принято.** Сейчас только `-s <ssh-алиас>`; адрес API и клиентский сертификат появятся вместе с работающим API |
| 4 MED | `deploy_timeout` — свойство приложения, не сервера | **принято.** Остаётся у приложения с общим значением по умолчанию: время старта у Convex и у статики разное |
| 5 MED | `covered()` не исчезает — выбор сертификата по host нужен всё равно | **принято.** Остаётся одна функция выбора TLS по host и серверной конфигурации. Данные переезжают, абстракция «сервер подставляет пути» не вводится |
| 6 MED | `env`→bws смешивает декларацию потребности с добычей секрета | **принято в суженном виде.** Поле называется `secrets`, область поиска в bws — одно правило, значения разрешаются на границе команды, `Options.Env` остаётся как есть. Интерфейса провайдеров секретов не вводим |
| 7 MED | проверку пары crt/key выбрасывать нельзя | **принято.** Прерывание установки двух файлов возможно и на сервере. Уходят только ветки и сообщения, специфичные для `Pull` |
| 8 LOW | `domains` списком сохраняет SAN-модель и имя файла от первого элемента | **принято.** Одно поле `wildcard`, фиксированные пути файлов на сервере, `Slug()` уходит |

## Итоговая форма

Конфиг приложения (`boks.yml` в его репозитории):

```yaml
app: convex-lab
image: ghcr.io/get-convex/convex-backend
ports:
  - {name: api, port: 3210, host: api.lab.kopanda.ru, health_path: /version}
  - {name: actions, port: 3211, host: actions.lab.kopanda.ru, health_path: /version, health_port: 3210}
volumes: [data:/convex/data]
secrets: [INSTANCE_NAME, INSTANCE_SECRET]
vars: {DISABLE_BEACON: "true", CONVEX_CLOUD_ORIGIN: "https://api.lab.kopanda.ru"}
deploy_timeout: 60s
```

Конфиг сервера (`/etc/boks/server.yml`):

```yaml
network: boks
proxy_image: basecamp/kamal-proxy:v0.10.0
keep: 3
cert:
  wildcard: "*.lab.kopanda.ru"
  dns: cloudflare
  email: kan.evgenii.dev@gmail.com
  renew_days: 30
```

Сервер указывается флагом `-s <ssh-алиас>`; `contexts.yml` откладывается до `boksd`.

## Что исчезает из кода (после разбора — меньше, чем я заявлял сначала)

- `cert.Pull` и команда `boks cert pull` — вместе с переносом продления на сервер;
- отметка на приложение `<slug>.<app>.loaded`, `MarkLoaded`, раздвоение `Pending`/`ReloadPending`;
- `Cert.Slug()`, `Cert.Domains` как список;
- `EnvContent` в нынешнем виде (чтение локального .env) — заменяется выдачей из bws по именам;
- `servers`, `network`, `proxy_image`, `keep`, `tls` из конфига приложения.

Остаются, вопреки первому наброску: серверный отпечаток загруженного сертификата, проверка пары
crt/key, функция выбора TLS по host.

## Порядок реализации

1. `internal/config`: разделение на конфиг приложения и конфиг сервера, чтение серверного файла
   по SSH, `-s` в CLI. Тесты `config` переписать.
2. `internal/cert`: убрать `Pull` и отметку на приложение, оставить один отпечаток и проверку
   пары, перейти на `wildcard` и фиксированные пути. Из 17 тестов пакета останется около 8.
3. `internal/deploy`: брать серверные поля из серверного конфига, сохранить выбор TLS по host.
4. Продление на сервере — только после проверки, что DNS-токен с сервера принимается.

## Добавлено 2026-09-15: сеть (подтверждённый пробел)

Конфигурация обязана это выразить: сеть больше не поле приложения и не одна на сервер.

- `network` уходит из конфига приложения совсем — сеть выводится из имени: `boks-<app>`;
- в конфиге сервера остаётся только имя сети прокси (общая, для его собственного подключения);
- контейнер получает `--network-alias <app>` — стабильное имя внутри своей сети;
- снятие приложения убирает его сеть;
- возврат compose (условие автора — всё внутри внутренней сети) выражается списком `services`
  с запретом `build:` и `ports:`.
